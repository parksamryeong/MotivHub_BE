# 트러블슈팅 기록

개발하면서 발견한 문제와 해결 과정을 기록한다. 사소한 것은 넣지 않고, "문제 → 원인 → 해결 → 결과"로 정리할 만한 것만 남긴다.

형식:

## [날짜] 문제 제목

- **상황**: 무엇을 하다가 발견했는지
- **원인**: 왜 그런 문제가 생겼는지
- **해결**: 어떻게 고쳤는지
- **결과**: 수치 변화가 있다면 (TPS, 응답시간, 에러율 등)

## [2026-10-06] 이슈 검색(LIKE 풀스캔) 부하테스트 — 데이터가 버퍼풀을 넘어서면 치명적 병목 발견

- **상황**: 이슈 게시판이 전사 공개(워크스페이스 스코프 없음, 의도된 설계)라 이슈 수가 회사 전체
  규모로 계속 늘어날 수 있는데, `IssueRepository.searchByKeyword`가 앞뒤 와일드카드 LIKE를
  `title`/`problemDescription`/`solution` 3개 컬럼에 OR로 걸고 있어서(인덱스 사용 불가) 데이터가
  늘어나면 느려질 수 있다는 우려가 있었다. 기존 부하테스트(`mixed-read-load-test.js`)는 `GET
  /api/issues`를 검색어 없이만 호출해서, 이 검색 경로 자체는 한 번도 부하테스트된 적이 없었다.
- **방법**: 두 단계로 나눠서 측정했다.
  1. `load-test/seed-issue-search-data.sql` + `issue-search-load-test.js`: 이슈 10,000건(400건 중
     1건꼴로 테스트 키워드 매칭, 총 25건) 시드 후 VU 10/20/30으로 측정.
  2. `load-test/seed-issue-search-data-large.sql` + `issue-search-load-test-large.js`: 이슈
     500,000건(1,250건 매칭) 시드 후 같은 VU 10/20/30으로 재측정. 이 규모(설명 텍스트만 약 550MB)는
     이 프로젝트의 MySQL `innodb_buffer_pool_size` 기본값(128MB, 로컬·운영 둘 다 커스텀 설정 없이
     기본값 그대로 — `SELECT @@innodb_buffer_pool_size`로 직접 확인)을 몇 배 넘어서도록 의도적으로
     설계했다. 50만 건을 단순 재귀 CTE로 만들면 느려서, 작은 수열 2개(1000×500)를 교차곱(CROSS
     JOIN)하는 방식으로 빠르게 생성했다.
- **원인**: 앞뒤 와일드카드 LIKE(`LIKE '%keyword%'`)는 B-tree 인덱스를 전혀 못 쓴다 — MySQL이 매
  요청마다 테이블 전체를 처음부터 끝까지 훑어야 한다. 데이터가 버퍼풀(메모리)에 다 들어가는
  동안에는(1만 건, ~11MB) 이 스캔이 CPU 비용만으로 끝나서 빠르지만, 버퍼풀을 넘어서면(50만 건,
  ~550MB) 매 스캔마다 디스크 I/O가 끼어들어 비용이 폭발적으로 늘어난다.
- **결과**:

  | 규모 | 단일 요청 | VU 10 | VU 20 | VU 30 |
  |---|---|---|---|---|
  | 1만 건(버퍼풀 안) | ~150ms | 실패율 0%, p95 236ms | 실패율 0%, p95 229ms | 실패율 0%, p95 285ms |
  | 50만 건(버퍼풀 초과) | **50.58초** | **100% 타임아웃(k6 기본 60초)** | **100% 타임아웃** | **100% 타임아웃** |

  1만 건 규모에서는 세 VU 단계 모두 p95가 230~285ms 범위에서 안정적이라 병목이 없었다. 반면 50만 건
  규모에서는 단일 요청만으로도 50초가 걸렸고, 동시 요청이 10개만 몰려도 전부 60초 타임아웃으로
  실패했다 — VU 10/20/30 사이에 유의미한 차이가 없었던 건 이미 요청 하나만으로도 완전히 망가진
  상태였기 때문이다.
- **해결**: MySQL FULLTEXT 인덱스(`ALTER TABLE issue ADD FULLTEXT INDEX ft_issue_search (title,
  problem_description, solution) WITH PARSER ngram`)로 전환해서 `LIKE` 대신 `MATCH() ...
  AGAINST() IN NATURAL LANGUAGE MODE`를 쓰도록 고쳤다 — 역색인 구조라 풀스캔 자체가 필요 없어진다.
  `ngram` 파서는 한국어 조사가 붙은 단어(예: "키워드가")도 검색어("키워드")로 찾아야 해서
  필수였다(기본 FULLTEXT 파서는 공백 기준 단어 분리라 이 케이스를 못 찾음). JPQL이
  `MATCH()/AGAINST()`를 표현 못 해서 네이티브 쿼리로 "관련도순 ID 목록"만 가져온 뒤, 기존과 같은
  `JOIN FETCH` JPQL 쿼리로 author/workspace를 N+1 없이 한 번 더 가져오고 자바에서 재정렬하는
  2단계 구조로 구현했다(`docs/superpowers/specs/2026-10-06-issue-search-fulltext-index-design.md`).
  검색 결과 정렬이 최신순에서 관련도순(`MATCH() 점수 DESC`, 동점 시 `created_at DESC`)으로 바뀐다.
- **결과(수정 전/후, 50만 건·버퍼풀 초과 규모로 동일 조건 재검증)**:

  | 지표 | 수정 전 | 수정 후 | 개선 |
  |---|---|---|---|
  | 단일 요청(HTTP) | 50.58초 | 3.27초 | **약 15배** |
  | 단일 요청(DB 쿼리만) | 측정 안 함(풀스캔 자체가 끝나지 않음) | 0.057초 | — |
  | VU 10 (처리량/p95) | 100% 타임아웃(처리량 0) | **7.04 req/s, p95 512ms** | 타임아웃 → 정상 |
  | VU 20 (처리량/p95) | 100% 타임아웃(처리량 0) | **13.57 req/s, p95 833ms** | 타임아웃 → 정상 |
  | VU 30 (처리량/p95) | 100% 타임아웃(처리량 0) | **15.27 req/s, p95 1.14초** | 타임아웃 → 정상 |

  VU 30에서 1분간 941개 요청 전부 성공(실패율 0%), 매칭 건수(1,250건)도 매 요청마다 정확했다.
  재검증 중 테스트 데이터 자체의 버그도 하나 발견했다 — 검색 키워드(`BOTTLENECKPROBELARGE`)의
  끝부분 "LARGE"가 시드 데이터의 이슈 제목("...issue (large) N")과 ngram 2글자 단위로 겹쳐서,
  50만 건 거의 전부가 엉뚱하게 매칭되는 현상이 있었다(실제 검색 로직의 버그가 아니라 테스트
  키워드 선정 실수). 겹치지 않는 키워드(`QZPLUMBUS`)로 교체해서 해결했다.

## [2026-10-06] 공동편집 Awareness(커서 중계) 부하테스트 — 유의미한 발견 없음

- **상황**: 공동편집에 커서 위치 중계 채널(`/topic/tasks/{id}/{field}/awareness`,
  `TaskEditRelayController.relayAwareness`)을 추가한 뒤, 기존 공동편집 테스트와 같은 패턴으로 정합성
  부하테스트를 해봤다.
- **방법**: `load-test/awareness-correctness-test.js`. 발신자 3/5/10명이 각자 20개 업데이트를 50ms
  간격으로 전송(기존 편집 테스트 대비 4배 빈도 — 커서는 타이핑보다 훨씬 자주 바뀔 수 있다는 근거),
  옵저버가 받은 총합과 비교.
- **결과**: 3/5/10명 전부 유실 0건(60/60, 100/100, 200/200), 지연시간 avg 1.2~4.9ms.
- **결론**: **예상대로 유의미한 발견 없음**. 이 채널은 Redis 버퍼도 공유 상태도 없는 순수 relay라서,
  프레즌스(O(N²))나 공동편집 버퍼(타이밍 레이스)처럼 "동시성이 늘면 성질이 달라지는" 지점 자체가
  없다 — 테스트 전부터 예측했던 결과가 그대로 나온 것. 회귀 방지 확인 이상의 의미는 없고, 지연시간
  수치도 "다음 브로드캐스트 도착까지의 간격"이라 동시 발신자가 많을수록 자연히 작아지는 근사치일
  뿐, 실제 relay 속도가 빨라진 건 아니다.

## [2026-10-05] 실시간 공동편집(CRDT 릴레이) 최초 부하테스트 — 정합성 중심

- **상황**: 지금까지 WebSocket 관련 부하테스트(프레즌스 동시입장 스톰, 보드 브로드캐스트 팬아웃, 프레즌스
  O(N²) 재검증)를 여러 번 했지만, 이 프로젝트의 핵심 차별 기능인 실시간 공동편집(`TaskEditRelayController`/
  `TaskEditBufferService`/`TaskEditAutosaveScheduler`가 담당하는 Yjs CRDT 업데이트 릴레이·버퍼링·
  자동저장 경로)은 한 번도 부하테스트한 적이 없었다. 이 기능의 트러블슈팅 이력을 보면 지금까지 발견된
  버그가 전부 "처리량"이 아니라 "동시성/타이밍 정합성" 문제였어서(UNSUBSCRIBE destination 누락, 저장
  요청 후 버퍼를 비우면 안 되는 레이스, TTL 갱신으로 인한 무한 재발송 루프 등), 이번 테스트는 프레즌스
  처럼 "몇 명까지 버티나"가 아니라 **"동시 타이핑 시 업데이트가 유실 없이 전달되고 최종 저장 내용이
  정확한가"**를 주 목적으로 설계했다.
- **방법**: `TaskEditRelayController`가 CRDT를 파싱하지 않고 그대로 릴레이·버퍼링만 하는 구조(relay-only)
  라는 걸 코드로 확인한 뒤, 임의 문자열을 "타이핑 업데이트"로 사용하는 k6 스크립트
  (`load-test/co-editing-correctness-test.js`)를 작성했다. VU1(옵저버, 구독만)·VU2(제출자, 타이핑+
  저장요청 수신 시 스냅샷 전송+REST 검증)·VU3 이상(일반 편집자)으로 역할을 나눠, 편집자 3/5/10명이
  각자 5개의 업데이트를 200ms 간격으로 동시 전송한 뒤, 옵저버가 받은 총 메시지 수와 편집자들이 보낸
  총합을 비교해 유실 여부를 확인하고, 자동저장 후 `GET /api/tasks/{id}/note`로 실제 저장된 내용이
  정확한지 검증했다.
- **1차 결과(오염됨)**: 1차 실행 중 k6 버전 호환성 문제(`k6/ws`의 Socket 객체에 `clearInterval`이
  없음 - 이 환경의 k6 2.2.0 기준)로 3명 케이스(run1)가 한 번 중간에 크래시했다가 수정 후 재시도했는데,
  이때 이미 Redis에 남아있던 버퍼의 `firstUpdateAt` 때문에 `max-wait-seconds`(15초) 임계값이 비정상적
  으로 일찍 넘어서 저장 신호가 70ms만에 나가는 오염된 값이 나왔다(코드 리뷰로 원인 역추적 - 직접 Redis
  조회로 확정한 건 아니고 코드 근거 추론).
- **2차 결과(버퍼 비우고 재실행, 신뢰 가능)**: Redis의 `task:edit-buffer:90001:note` 관련 키를 비우고
  3명 케이스만 다시 실행해서 최종 결과를 확정했다:

  | 편집자 수 | 보낸/받은 업데이트 | 유실 | 저장 검증 | edit_relay_latency_ms (avg/p95) | autosave_signal_latency_ms |
  |---|---|---|---|---|---|
  | 3 | 20 / 20 | 0건 | PASS | 24.4 / 102 | 3154ms |
  | 5 | 30 / 30 | 0건 | PASS | 2.2 / 3 | 3546ms |
  | 10 | 55 / 55 | 0건 | PASS | 1.9 / 4 | 3444ms |

  세 단계 모두 업데이트 유실 0건, 저장 내용 100% 정확. `autosave_signal_latency_ms`(마지막 타이핑 후
  저장 요청 신호까지 걸리는 시간, 이번에 처음 측정한 지표)는 편집자 수와 무관하게 3100~3550ms로
  거의 평평하다 — `TaskEditAutosaveScheduler`의 설정값(idle-seconds=3초 + 폴링 주기 최대 1초)과
  정확히 일치하는 이론값이다. 버퍼가 태스크·필드 단위로 공유되고(`appendUpdate`가 누가 보내든 같은
  `lastUpdateAt`을 갱신) 자동저장 판단도 그 공유 타임스탬프 기준이라, 동시 편집자 수가 늘어도 "저장
  까지 걸리는 시간" 자체는 늘어나지 않는다는 게 실측으로 확인됐다.
- **결론**: 공동편집의 핵심 경로(릴레이·버퍼링·자동저장)는 테스트한 범위(동시 편집자 3~10명)에서
  정합성·지연시간 모두 건강하다. 이번 라운드에서 새로 발견된 버그는 없음 — 오염된 1차 결과도 테스트
  스크립트/환경 쪽 문제였지 백엔드 로직 결함이 아니었다.

## [2026-10-05] 프레즌스 O(N²) 브로드캐스트 증폭 수정 및 재검증

- **상황**: 2026-09-27 "실시간(WebSocket/STOMP) 기능 최초 부하테스트"에서 발견하고 "다음 후보(배치 디바운스,
  델타만 브로드캐스트)로 남긴다"라고만 기록해뒀던 프레즌스 O(N²) 브로드캐스트 문제를 실제로 고쳤다.
  `TaskPresenceEventListener`가 SUBSCRIBE/UNSUBSCRIBE/DISCONNECT 이벤트마다 배치 없이 매번 전체 뷰어
  목록을 재브로드캐스트하던 구조를, 신규 `PresenceBroadcaster`의 leading+trailing 디바운스(쿨다운
  200ms, 폴링 100ms)로 교체했다 — 쿨다운 전이면 즉시 1회 전송(leading edge), 쿨다운 중 추가 이벤트는
  pending으로만 쌓아뒀다가 스케줄러가 마무리로 딱 1회만 전송(trailing edge). 메시지 포맷
  (`TaskPresenceMessage`)은 그대로라 프론트엔드 변경이 전혀 없었다.
- **원인**: (9/27에 이미 분석 완료 — 매 이벤트마다 그 시점까지의 전체 뷰어 목록을 모든 구독자에게
  재전송하는 구조라, N명이 거의 동시에 입장하면 총 브로드캐스트가 1+2+...+N ≈ N(N+1)/2로 증가)
- **해결**: 위 디바운스 설계. 기존 `TaskEditAutosaveScheduler`(자동저장 폴러)와 동일한
  `@Value`/`@Scheduled(fixedDelayString=...)` 패턴을 재사용해서 코드베이스 일관성을 유지했다. 최종
  코드 리뷰에서 추천받은 대로 `flushPending()`의 per-task 루프에 try/catch를 추가해서(기존
  `TaskEditAutosaveScheduler.triggerDueSaves()`와 동일한 패턴), 한 태스크의 브로드캐스트 실패가 같은
  틱의 나머지 태스크 처리를 막지 않도록 방어했다.
- **결과**: 같은 `load-test/websocket-presence-storm-test.js`로 VU10/30/50/100 각각 "한 번에 N명이
  동시 입장"하는 단일 버스트(`-u N --iterations N`)를 재실행해서 비교했다:

  | VU | 연결당 평균 메시지 수 (수정 전, 9/27) | 연결당 평균 메시지 수 (수정 후) |
  |---|---|---|
  | 10 | 11.0 | 3.0 |
  | 30 | 35.5 | 2.4 |
  | 50 | 59.3 | 3.9 |
  | 100 | 92.9 | 2.6 |

  수정 전엔 N에 거의 비례해서 늘어나던 값이(이론적 O(N²) 총량과 일치), 수정 후엔 N과 무관하게
  2~4 사이에서 거의 평평하다 — 설계대로 "버스트 하나당 브로드캐스트 최대 2회"로 트리거 횟수가
  고정된 결과(최종 전송 횟수는 여전히 그 시점 구독자 수만큼 팬아웃되지만, *트리거되는 횟수* 자체가
  O(N)에서 O(1)로 줄어든 것). 기존 `TaskPresenceEventListenerTest`(STOMP 통합 테스트 6개)도 로컬
  Docker 환경에서 3회 연속 재실행해 전부 통과 확인 — 디바운스 도입으로 단일 입장/퇴장의 즉시성(leading
  edge)이 깨지지 않았다는 걸 기존 테스트 스위트로도 재확인한 셈이다.

  **추가 검증 (VU200/300까지 밀어보기)**: 디바운스가 더 높은 동시성에서도 버티는지, 그리고 최종 코드

    오염이었다 - 이 지표가 "구독 후 첫 메시지"가 아니라 "그 연결이 받은 모든 메시지 각각"의

## [2026-09-28] 이메일 인증 기능 첫 배포 때 겹친 장애 2건 (메일 미발송 401 오표시 + Naver "unused" 값 삭제로 인한 부팅 실패)

- **상황**: 이메일 인증코드 회원가입 기능을 EC2에 처음 배포(이 기능은 이번이 처음 실제 배포 -
  Flyway 스키마가 v22에서 바로 v23~25로 올라간 것으로 확인, 로컬 테스트만 있었음). 배포 직후
  헬스체크(`/actuator/health/readiness`, `/liveness`)는 UP이었지만, 실제로
  `/api/auth/signup/request-verification`을 호출하면 401(`"인증이 필요합니다."`)이
  떨어졌다 - `SecurityConfig`의 `PUBLIC_ENDPOINTS`에 `/api/auth/signup/**`이 이미 있었고
  로컬 테스트도 전부 통과한 상태라 처음엔 원인을 알 수 없었다.
- **원인 1 (메일 발송 실패가 401로 잘못 보임)**: 이 EC2에는 `MAIL_USERNAME`/`MAIL_PASSWORD`가
  한 번도 설정된 적이 없었다(기존에는 actuator 헬스체크에서만 보이는 무해한 false negative로
  기록돼 있었는데 - 이메일 인증 기능 자체가 실사용된 적이 없어서 지금까지는 문제가 안 됐던
  것). `EmailVerificationMailService.sendVerification()`이 던지는
  `MailAuthenticationException`을 `GlobalExceptionHandler`가 처리하지 않아서 그대로
  흘러갔고, 처리 안 된 예외가 컨테이너의 기본 `/error` 디스패치로 넘어갔는데 `/error`는
  `SecurityConfig`의 공개 경로 목록에 없어서 원래 500이어야 할 응답이 인증 필요(401)로
  둔갑했다. `/api/auth/signup/complete`처럼 Bean Validation에서 먼저 걸리는 요청은 이
  경로를 안 타서 정상(400)이었기 때문에, "왜 signup 중 하나만 401이지?"가 진단을 헷갈리게
  만든 포인트였다 - `docker exec`로 컨테이너 안에서 직접 curl을 쏘고 그 직후 로그를
  대조해서(`SignupService.requestVerification` → `EmailVerificationMailService.sendVerification`
  스택트레이스) 실제 원인을 특정했다.
- **해결 1**: `GlobalExceptionHandler`에 `MailException` 핸들러를 추가해서 503으로 명확하게
  응답하도록 함 - 예외가 컨트롤러 밖으로 안 나가므로 `/error` 디스패치 자체가 필요 없어져서
  근본적으로 해결됨(메일 서버가 죽어도, 자격증명이 잘못돼도 항상 503으로 정확히 보임).
- **원인 2 (수정 배포 직후 부팅 자체가 실패)**: 위 수정을 배포하려고 EC2 `.env`에
  `MAIL_USERNAME`/`MAIL_PASSWORD`를 추가하던 중, "네이버 로그인은 프론트에서 안 쓰니까
  unused"라고 판단해서 `NAVER_CLIENT_ID`/`NAVER_CLIENT_SECRET` 줄을 같이 지웠다. 그런데
  `application.yaml`은 `naver` OAuth2 client registration을 여전히 선언하고 있었고,
  Spring Boot의 `OAuth2ClientProperties`는 선언된 모든 registration의 client-id가
  비어있지 않은지 앱 시작 시점에 강제로 검증한다(`IllegalStateException: Client id of
  registration 'naver' must not be empty.`) - 그 결과 컨테이너가 계속 재시작 루프에
  빠졌다. 테스트에서는 `application-test.yaml`에 네이버용 더미 값이 항상 박혀 있어서
  이 문제가 전혀 안 잡혔던 것도 원인 중 하나 - "안 쓰는 값"이라는 판단이 코드(YAML
  registration 선언) 쪽에서는 여전히 "필수 값"이었던 셈.
- **해결 2**: 임시로 `.env`에 더미 값을 넣어 즉시 복구한 뒤, `application.yaml`과
  `application-test.yaml`에서 `naver` registration/provider 선언 자체를 완전히 제거해서
  "프론트에서 안 쓴다 = 백엔드도 이 값이 더 이상 필요 없다"를 실제로 맞춰놨다. `NaverUserInfo`,
  `SocialProvider.NAVER` 등 순수 Java 코드는 그대로 뒀다(OAuth2 client registration이
  없으면 그냥 도달 불가능한 죽은 코드가 될 뿐, 별도 위험 없음).
- **결과**: 메일 발송(실제 구글 계정 앱 비밀번호로 설정) 확인 후 재배포 → 헬스체크 UP,
  `request-verification` 200 확인, 실제 수신함에 인증코드 메일 도착까지 확인. "환경변수가
  비어있으면 무해하다고 알고 있던 값"이 실제로는 앱 구동을 막을 수 있다는 게 재확인된 사례 -
  프론트에서 안 쓰는 기능이라도, 백엔드 설정(특히 Spring Boot의 `@ConfigurationProperties`
  검증처럼 시작 시점에 강제되는 것)에 여전히 걸려있으면 "unused니까 지워도 된다"는 판단이
  바로 장애로 이어진다.

## [2026-09-28] 이메일 인증을 링크→6자리 코드로 바꾸면서 생긴 잠금 우회 취약점 2건

- **상황**: 이미 merge된 "메일 링크 클릭" 방식의 이메일 인증을 "6자리 코드 입력"(같은 화면에서 끊김없이
  처리하기 위함) 방식으로 바꿨다. UUID 토큰(122비트, 사실상 추측 불가)을 6자리 숫자(약 20비트,
  100만 가지)로 바꾸는 거라 브루트포스 방지책(5분 만료 + 틀린 시도 5회 제한)을 같이 넣었는데,
  merge 직전 최종 전체 리뷰(가장 유능한 모델로 브랜치 전체를 다시 훑는 단계)에서 이 방지책이
  실질적으로 아무 효과가 없다는 게 드러났다. 태스크 단위 리뷰(각 파일/각 태스크만 보는 리뷰)에서는
  전혀 안 걸렸다 - 시스템 전체를 공격자 관점에서 추적해야만 보이는 문제였다.
- **원인 (두 가지 조합)**:
  1. **재발급으로 시도 횟수가 무한 리셋됨**: 시도 횟수(`attemptCount`)를 인증코드 row 하나에
     저장했는데, `request-verification`(재발급) API에 호출 제한이 전혀 없었다. 공격자가
     "재발급 → 아무 코드나 5번 시도"를 계속 반복하면, 호출할 때마다 매번 새 코드 + 새로운
     시도 5회를 받는다. 이메일을 한 번도 열어보지 않고도 순수 확률로 뚫린다 - 대략 사이클당
     5/1,000,000 확률로 성공하고, 초당 50요청 정도면 몇 시간 안에 성공 확률 50%대에 도달한다.
     게다가 재발급마다 피해자에게 진짜 메일이 가므로 같은 공격이 메일 폭탄이자 메일 발신
     계정의 평판/한도 소모 공격도 겸한다.
  2. **시도 횟수 증가 자체가 레이스 컨디션**: `completeSignup`이 시도 횟수를 "읽고 +1해서
     저장"하는 방식(`recordFailedAttempt()` → Hibernate dirty check로 절대값 저장)이었는데,
     엔티티에 `@Version`도, 조회에 락(`@Lock`)도 없었다. 동시에 여러 요청을 보내면 전부 같은
     값을 읽고 같은 값+1을 써서, 100개를 동시에 보내도 카운터가 1만 올라간다 - 5회 제한이
     사실상 수백 회로 뚫린다.
  - 두 문제를 합치면, 재발급 자체를 안 해도(2번만으로) 5회 제한이 유명무실해지고, 재발급까지
    더하면(1번) 5분/5회 방지책 전체가 사실상 존재하지 않는 것과 같아진다.
  - 참고로 태스크 2 리뷰 단계에서 별도로 발견/수정한 것: 시도 횟수 증가(`recordFailedAttempt()`)
    직후 `VerificationCodeMismatchException`을 던지는데, `@Transactional` 기본 롤백 규칙 때문에
    이 증가분이 커밋되지 않고 매번 롤백되는 문제도 있었다(`noRollbackFor` 어노테이션으로 임시
    수정) - 이것도 "5회 제한이 사실상 작동 안 함"에 기여하던 별개의 버그였는데, 지금 아래 해결책
    (Redis 기반 카운터)으로 넘어가면서 이 우회 코드 자체가 필요 없어질 예정이다.
- **해결**: 시도 횟수를 DB 컬럼(코드 row당)이 아니라 **Redis에 이메일당 카운터**로 옮겼다.
  Redis의 `INCR`은 원자적이라 레이스 컨디션이 원천 차단되고(2번 해결), 이 카운터는 코드가
  재발급돼도 이메일 기준으로 그대로 유지되므로 재발급으로 시도 횟수가 리셋되는 것도
  막힌다(1번 해결). 재발급 자체에도 짧은 쿨다운(30초, 테스트 프로파일은 0으로 비활성화)을
  추가해서 무한 반복 재발급 자체를 막는다. `noRollbackFor` 우회 코드도 통째로 제거했다(더
  이상 DB 트랜잭션 안에서 시도 횟수를 다루지 않으므로).
  - **1차 구현의 숨은 결함 2개 (재검토에서 추가로 발견)**: Redis 카운터를 처음 넣었을 때는
    이메일 대소문자 정규화가 어디에도 없어서, Redis 키(`Victim@x.com`과 `victim@x.com`은
    서로 다른 키)와 DB 조회(`utf8mb4_0900_ai_ci` 콜레이션이라 대소문자 구분 안 함)가
    어긋났다 - 이메일 하나당 대소문자 변형 개수만큼(16자 이메일이면 2^16가지) 독립된
    5회 한도와 독립된 쿨다운을 새로 받을 수 있어서 1번 문제가 사실상 그대로 남아 있었다.
    또한 "확인(GET) → DB 조회 → 코드 비교 → 증가(INCR)" 순서로 짜여 있어서, 확인과 증가
    사이에 DB 왕복이 끼어 있는 check-then-act 구조라 동시 요청이 몰리면 전부 확인을
    통과한 뒤에야 카운터가 올라가는 2번과 같은 종류의 경쟁이 재발했다. 두 문제 다 태스크
    리뷰가 아니라 이 수정 자체를 다시 검토하는 별도 단계에서 잡혔다.
  - **2차 수정**: (a) `SignupService`의 `requestVerification`/`completeSignup` 진입부에서
    이메일을 `trim().toLowerCase()`로 정규화한 뒤 그 값만 Redis 키/DB 조회/저장에 쓰도록
    통일. (b) `VerificationAttemptLimiter`를 "확인 후 증가"가 아니라 "먼저 Lua 스크립트로
    INCR+EXPIRE를 원자적으로 실행해서 순번을 예약하고, 그 결과가 한도를 넘으면 코드 비교
    자체를 하지 않는" 방식으로 전환 - 예약이 원자적이므로 동시 요청이 몇 개가 몰리든 정확히
    5개까지만 코드 비교까지 도달한다. 덤으로 INCR과 EXPIRE를 하나의 스크립트로 묶어서, 둘
    사이에 프로세스가 죽으면 TTL이 영영 안 걸려 영구 잠금이 되는 마이너 버그도 같이 없앴다.
  - **2차 수정에도 남아있던 3번째 결함 (또 다른 재검토에서 발견)**: `trim().toLowerCase()`는
    "대소문자"만 정규화하지, MySQL 기본 콜레이션(`utf8mb4_0900_ai_ci`)이 같은 값으로 취급하는
    "악센트"와 "전각문자"는 정규화하지 못한다 - 즉 `víctim@x.com`이나 전각 유니코드로 쓴
    이메일도 DB 조회에서는 `victim@x.com`과 같은 row로 잡히지만, Java 쪽에서는 서로 다른
    문자열이라 Redis 키가 갈라진다. 결국 대소문자만 다른 게 아니라 악센트/전각문자로 변형한
    이메일마다 독립된 5회 한도 + 독립된 쿨다운을 새로 받을 수 있어서, 문자 종류만 바뀌었을 뿐
    1번 문제(재발급/변형으로 시도 횟수 우회)가 그대로 남아 있었다. 로컬 MySQL에 직접 쿼리해서
    `'víctim@x.com' = 'victim@x.com'`이 1을 반환하는 것으로 재현 확인.
  - **3차 수정**: 클라이언트가 보낸 문자열을 아무리 정규화해도 DB 콜레이션이 인식하는 모든
    동치 관계(대소문자+악센트+전각문자)를 Java 코드로 다 따라잡기는 어렵다는 점을 인정하고,
    접근 자체를 바꿨다 - Redis 키를 "클라이언트가 이번에 보낸 문자열"이 아니라 "DB가 이미 같은
    계정으로 판단해서 토큰 row에 저장해 둔 정규 표기"(`verificationToken.getEmail()`)로 쓰도록
    변경. `completeSignup`은 토큰을 먼저 조회한 뒤 그 토큰의 이메일로 시도 횟수를 세고,
    `requestVerification`도 기존 미소비 토큰이 있으면 그 토큰의 이메일로 쿨다운을 건다 -
    DB의 동치 판단 결과를 그대로 재사용하므로 어떤 변형이 오든 항상 같은 Redis 키로 수렴한다.
    악센트 변형 이메일로 5회 한도를 공유하는지 검증하는 회귀 테스트 추가.
  - **3차 수정에도 남아있던 4번째 결함 (역시 재검토에서 발견)**: "정규 표기를 쓴다"는 원칙을
    `completeSignup`의 시도 횟수 카운터와 `requestVerification`의 쿨다운 확인에는 적용했지만,
    정작 재발급 시 새로 저장하는 토큰 row 자체는 "이번 요청이 보낸 원본 문자열"로 저장하고
    있었다 - 즉 쿨다운 "확인"에는 정규 표기를 쓰면서, 그다음 줄에서 만드는 새 row는 확인에
    안 쓴 값으로 만든 것. 그 결과 재발급할 때마다 "정규 표기" 자체가 공격자가 이번에 보낸
    변형으로 계속 갱신돼서, 그다음 `completeSignup` 호출은 그 새로운(공격자가 정한) 표기를
    기준으로 카운터를 세게 됐다 - 재발급 한 번마다 카운터가 또 리셋되는 1번 문제가, 이번엔
    "확인"과 "저장"이 서로 다른 값을 쓰는 사소한 불일치를 통해 한 단계 우회해서 되살아난
    것. 유일하게 남은 방어선인 30초 쿨다운만 뚫으면 되므로, 무제한 우회가 "30초에 5번"으로
    줄어들었을 뿐 - 원래 의도(30분에 5번)보다 약 60배 많은 시도가 가능했다.
  - **4차 수정**: `requestVerification`에서 쿨다운 확인에 쓴 정규 표기 변수를 그대로
    재사용해서 새 토큰 row 저장과 메일 발송 대상까지 통일했다 - 이제 한 이메일에 대해 처음
    한 번 정해진 표기가 그 이메일의 인증이 끝날 때까지(가입 성공 또는 완전히 새로운 최초
    요청 전까지) 절대 바뀌지 않는다. 재발급 시 다른 대소문자로 요청해도 카운터가 안 풀리는지
    검증하는 회귀 테스트 추가.
  - **총 4번의 독립 재검토에서 매번 다른 각도의 우회를 하나씩 찾아냈다는 점 자체가 교훈이다**:
    "정규화했다", "정규 표기를 쓴다"는 확인 한 번으로는 부족했고, 그 원칙이 코드의 **모든**
    관련 지점(확인 지점뿐 아니라 그 값이 다음 사이클로 이어지는 저장 지점까지)에 빠짐없이
    적용됐는지를 매번 다시 추적해야 했다. 유니코드 동치 관계를 Java 코드로 나열하는 접근(2·3차)
    대신 "DB가 이미 내린 판단을 그대로 재사용"하는 접근(3차 이후)으로 바꾼 것 자체는 옳았지만,
    그 판단 결과를 일관되게 전파하는 것과 그 판단을 다시 계산하는 것은 별개의 문제였다.
- **별도 발견 (I1, 배포 관련)**: 새 마이그레이션(V25, `token` 컬럼을 `code`로 축소)이 테이블에
  기존 row가 있으면 실패한다(36자 UUID가 6자 컬럼에 안 들어감, MySQL strict mode에서 에러) -
  이전 링크 방식(V24)은 이미 PR #31로 main에 merge돼 배포됐을 수 있어서, 실제 환경 테이블에
  UUID row가 남아 있을 가능성을 배제할 수 없었다. 마이그레이션 맨 앞에
  `DELETE FROM email_verification_token;`을 추가해서 해결(이 테이블은 최대 5분짜리 인증
  코드만 담으므로 비워도 안전). "이번 브랜치가 merge된 적 없어서 안전하다"고 처음 판단했던 건
  부정확했다 - 안전한 이유는 브랜치가 아니라 이 테이블/기능 자체가 실사용된 적이 없어서였다.
- **결과**: Redis 이메일당 카운터 + 원자적 예약(Lua INCR+EXPIRE) + DB 정규 표기를 저장 시점부터
  일관되게 유지(sticky) + 재발급 쿨다운 + 마이그레이션 DELETE 선행까지 적용한 뒤 전체 테스트
  스위트(대소문자 변형, 악센트 변형 각각의 카운터 공유 테스트, 서로 다른 대소문자로 재발급해도
  카운터가 안 풀리는 테스트, 동시 요청 20개로 원자성 검증하는 테스트 포함) 통과 확인. 총 4번의
  재검토(각각 독립된 리뷰 단계)에서 서로 다른 종류의 우회를 하나씩 찾아냈다는 점 자체가
  교훈 - "이메일을 정규화했다"는 확인 한 번으로는 부족했고, 매번 "이 정규화/정규 표기가 코드의
  모든 관련 지점에 빠짐없이, 그리고 다음 사이클까지 일관되게 전파되는가"까지 검증해야 했다.

  했다. 이제 이 값을 부하테스트 목적으로 계속 바꿔도(30, 60, 그 이상) 테스트 스위트는 영향받지 않는다.
- **결과**: 로컬 전체 스위트 재실행 - `BUILD SUCCESSFUL`, 539개 전부 통과.
- **교훈**: 여러 통합 테스트가 Testcontainers 인스턴스 하나를 공유하는 구조에서는, 운영/개발 설정
  파일의 리소스 관련 값(커넥션 풀 크기 등)을 테스트 프로파일이 절대 암묵적으로 상속하게 두면 안
  된다 - 운영 튜닝이 바뀔 때마다 테스트 스위트가 예측 불가능하게 깨질 수 있다. 진단할 때 "같은
  테스트를 단독으로 돌리면 통과한다"는 신호가 "전체 스위트 규모에서만 나타나는 리소스 누적 문제"의
  단서였고, `git worktree`로 base 브랜치와 직접 비교한 게 원인을 우리 PR로 확정하는 데 결정적이었다.

## [2026-09-27] 쓰기(POST/PATCH) API 부하테스트 - 댓글 작성의 동기식 알림 팬아웃이 진짜 병목

  허용해서, 시드 데이터의 담당자 배정 규칙(`태스크id 90001+n` -> 담당자 `90001+(n%10)`,

  몰리면 유독 나쁘게 나온다는 걸 이번에 확인(이전 라운드들의 읽기 시나리오보다 쓰기 시나리오에서
  이 효과가 훨씬 크게 나타남 - 쓰기가 커넥션을 더 오래 붙잡기 때문으로 추정).
- **HikariCP 30 -> 60으로 올려서 재검증**: 워밍업된 상태에서도 VU250에서 47.61%가 실패해서, 풀
  사이즈가 근본 원인이 아니라는 게 드러났다. 특히 세 가지 쓰기 분기의 실패율이 크게 갈렸다(VU250

  결정적 단서였다.
- **원인**: `NotificationEventListener.onTaskCommentCreated`가 `@TransactionalEventListener
  (AFTER_COMMIT)`이지만 `@Async`가 아니라서, 댓글의 INSERT 트랜잭션이 커밋된 뒤에도 **같은 HTTP
  요청 스레드에서 그대로 이어서** 수신자(담당자+감시자+작성자, 작성자 본인 제외)마다
  `NotificationService.notify()`를 순차 호출한다. 그런데 `notify()`는
  `@Transactional(propagation = REQUIRES_NEW)`라서 호출마다 완전히 새 트랜잭션(=새 HikariCP
  커넥션)을 연다. 즉 댓글 1건 = INSERT 트랜잭션 1개 + 수신자 수만큼의 REQUIRES_NEW 알림 트랜잭션을

  + 비동기 아님 + 수신자별 `notify()` 반복)이 `onAssigneeAdded`/`onChecklistCompleted`/
  `onDueDateApproaching`/`onTaskOverdue`에도 동일하게 존재한다.

## [2026-09-27] Tomcat 커넥터 한도가 HikariCP 병목을 가리고 있던 문제 — 2단계 발견

- **상황**: 2026-09-11 부하테스트에서 VU30 순간 버스트 시 HikariCP 활성 커넥션이 기본 풀 최대치(10)까지
  찼던 신호를 발견하고도 "다음 라운드에서 확인"이라고만 남기고 방치했었다. 이번 라운드에서 VU를
  30→50→80→100→150→200→300→350까지 단계적으로 올려가며 실제로 재현을 시도했다. 추가로
  2026-09-11에 시드만 해두고 한 번도 실제로 부하테스트하지 않았던 댓글/활동로그 API(태스크당 300개씩
  시드됨)도 `heavy-task-stress-test.js`에 섞어서 처음으로 측정했다.
- **원인**: 처음엔 HikariCP가 안 보였다 — VU100까지는 실패율 0%, 커넥션 획득 대기시간도 200ms 안팎에서
  거의 안 늘었다. VU150부터 간헐적 실패(0.3~0.8%)가 나왔는데, 앱 로그엔 에러가 전혀 없고 HikariCP
  타임아웃 카운트도 계속 0이었다 — 즉 요청이 애플리케이션 코드까지 도달하지도 못하고 있었다. 실패 응답을
  직접 캡처해보니 전부 `status=0, error="dial: connection refused"`였고, 전부 같은 순간(테스트 시작
  버스트)에 몰려있었다. `jvm_threads_peak_threads`가 193→231까지 오르는 것과 함께 보면, 원인은
  **Spring Boot 내장 Tomcat의 기본 커넥터 한도**(`server.tomcat.threads.max=200` +
  `accept-count=100`, 순간적으로 받을 수 있는 연결이 약 300개)였다 — HikariCP가 아니라 그 앞단에서
  이미 막히고 있었던 것.

  여기서 **2단계 발견**이 나왔다: Tomcat 한도만 올렸더니(`threads.max=400`, `accept-count=200`)
  connection-refused는 줄었지만, 이번엔 `hikaricp_connections_acquire_seconds_max`가 **2.03초**까지
  치솟았다 — Tomcat이 이제 더 많은 요청을 받아주면서, 그 요청들이 전부 여전히 HikariCP 커넥션 10개를
  두고 경합하게 된 것. 즉 **9/11에 처음 의심했던 HikariCP가 결국 맞았고**, 다만 Tomcat 커넥터 한도에
  가려져서 그동안 안 보이고 있었을 뿐이었다.
- **해결**: `application.yaml`에 두 설정을 함께 추가했다:
  - `server.tomcat.threads.max: 400`, `server.tomcat.accept-count: 200`
  - `spring.datasource.hikari.maximum-pool-size: 30`

  하나만 고쳤을 때 오히려 다른 쪽 병목이 드러나는 걸 직접 겪었기 때문에, 둘을 함께 올려야 한다는 걸

## [2026-09-01] 새로고침하면 로그인이 가끔 풀리는 문제

- **상황**: 멀티 디바이스 로그인 기능(기기별로 독립적인 세션 유지)을 검증하던 중, 기기A에서 로그아웃한 뒤 기기B를 새로고침했더니 기기B도 로그아웃되는 현상 발견. 처음엔 백엔드의 기기별 Redis 키 분리 로직이 잘못된 줄 알았음.

Redis에서 남은 세션의 refresh token을 직접 꺼내 `/api/auth/refresh`에 curl로 재생해봤더니 200이 정상적으로 돌아와서, 서버 로직은 이상이 없다는 걸 먼저 확인. 그 다음 프론트 코드를 비교해보니 `App.tsx`의 앱 부팅 `useEffect`에 React 18 StrictMode의 이중 실행 방지 가드가 없었음 — 같은 로직을 쓰는 `OAuthCallbackPage.tsx`에는 이미 `hasRun` ref 가드가 있었는데 부팅 로직에는 빠져있었음. StrictMode가 effect를 두 번 실행 → `/api/auth/refresh`가 거의 동시에 두 번 호출 → 첫 요청이 refresh token을 rotate하면 두 번째 요청은 이미 무효화된 토큰으로 401 → 그 401의 실패 처리가 방금 첫 요청이 저장한 정상 로그인 상태를 지워버림.
- **해결**: `App.tsx`의 부팅 effect에 `OAuthCallbackPage.tsx`와 동일한 `hasRun` ref 가드를 추가해서 중복 실행 방지.
- **결과**: 새로고침 시 세션이 안정적으로 유지됨. 이 과정에서 "증상은 프론트에서 보이지만 원인은 프론트/백엔드 중 어느 쪽인지" 구분하는 방법(서버가 들고 있는 실제 데이터를 직접 조회 + 같은 요청을 수동으로 재생해서 서버 로직만 따로 검증)을 정리하게 됨 — 이후에도 비슷한 종류의 버그를 볼 때 재사용 가능한 접근.

## [2026-09-02] 초대 무효화 API의 권한 우회 취약점

- **상황**: 워크스페이스 초대(링크/이메일) 기능 코드 리뷰 중 `WorkspaceInviteService.revokeInvite(ownerUserId, workspaceId, inviteId)`를 점검하다가 발견.

- **결과**: 리뷰 단계에서 배포 전에 잡힘. "권한 검사(OWNER 확인)"와 "리소스 소유 관계 검사(그 리소스가 그 상위 리소스 소속인지)"는 별개로 챙겨야 한다는 걸 코드에 남겨둔 사례.

## [2026-09-02] 목록 조회 API의 N+1 쿼리 개선

- **상황**: 워크스페이스 목록(`listMine`)과 태스크 목록(`listByWorkspace`) 조회 API 리뷰에서 각각 N+1 쿼리 패턴이 지적됨.

## [2026-09-06] Swagger/OpenAPI가 모든 프로필에서 인증 없이 공개되어 있던 문제

- **상황**: 워크스페이스/태스크 보완 작업(이름 수정 API, 초대 목록 조회 API, 응답 닉네임 embed) 완료 후 전체 브랜치 diff에 대한 최종 리뷰를 돌리던 중 발견. 이번 작업 범위는 아니었지만(springdoc-openapi Swagger 문서 추가는 그 이전 커밋에서 이미 들어간 상태) 리뷰 중 "이상한 게 있으면 알려달라"는 취지로 넓게 훑다가 걸림.
- **원인**: `SecurityConfig`의 `PUBLIC_ENDPOINTS`에 `/v3/api-docs/**`, `/swagger-ui/**`, `/swagger-ui.html`이 프로필 구분 없이 `permitAll`로 등록되어 있었고, springdoc 자체를 끄거나 프로필별로 조건화할 방법이 어디에도 없었음. 즉 실제 배포 환경에 그대로 올라가면 인증 없이 전체 API 명세(모든 엔드포인트, 모든 DTO 필드 구조)가 누구에게나 노출되는 구조. `application.yaml`에 이미 actuator에 대해서는 "로컬 전용, 실배포시 네트워크 격리/인증 반드시 추가"라는 주석이 있었는데, Swagger는 그런 주석이나 대비책 없이 추가된 것으로 보임.

## [2026-09-07] 활동 로그 컬럼 폭이 감사 대상 컬럼보다 좁아서 태스크 수정이 통째로 롤백되던 문제

- **상황**: 활동 로그 + 체크리스트 8개 태스크 SDD 작업 완료 후 전체 브랜치 최종 리뷰(가장 강력한 모델로 별도 실행)에서 발견. 태스크별 스코프 리뷰에서는 각 diff가 다 정상으로 보였는데, 전체를 한 번에 보는 단계에서만 드러난 케이스.
- **원인**: `TaskActivityLog.oldValue`/`newValue`는 `VARCHAR(500)`인데, 이 값에 그대로 들어가는 `Task.description`은 `VARCHAR(2000)`(최대 2000자 허용)였음. 500자 넘는 설명으로 `PATCH /api/tasks/{id}`를 호출하면 활동 로그 INSERT가 컬럼 폭을 넘겨서 MySQL strict mode에서 `DataIntegrityViolationException` 발생 → `@Transactional` 메서드 전체가 롤백 → 사용자 입장에선 정상적인 요청인데 500 에러와 함께 수정 내용이 통째로 날아감. Task 1(활동 로그 인프라)과 태스크 상세 정보(description 2000자 허용)는 서로 다른 태스크에서 각각 정상으로 구현됐지만, 둘의 "폭" 제약이 서로 안 맞는다는 건 두 diff를 동시에 안 보면 안 보이는 문제였음.
- **해결**: `TaskActivityLogService.record(...)`에서 `field`/`oldValue`/`newValue`를 각 컬럼 폭(30/500/500)으로 저장 전에 truncate하도록 방어 로직 추가 — 어떤 호출부가 와도 컬럼을 못 넘기게 원천 차단. 600자 설명으로 수정해도 예외 없이 성공하고 로그의 `newValue`가 정확히 500자로 잘리는지 회귀 테스트 추가.
- **결과**: "감사/로그용 스냅샷 컬럼의 폭은 그게 감사하는 원본 컬럼의 폭과 반드시 맞춰서 확인해야 한다"는 걸 남긴 사례. 태스크 단위 리뷰는 "이 diff가 스펙대로 됐는가"만 보고, 전체 리뷰가 "여러 태스크가 합쳐지면 뭐가 깨지는가"를 본다는 두 리뷰의 역할 차이를 실제로 보여준 케이스이기도 함.

## [2026-09-07] 체크리스트 orderIndex가 삭제 후 재사용되면서 정렬이 충돌하던 문제

- **상황**: 같은 최종 리뷰에서 함께 발견. 체크리스트 항목 추가(Task 5)와 삭제(Task 6)가 서로 다른 태스크에서 구현됐는데, 각 태스크의 스코프 리뷰는 "이 태스크가 요구사항대로 됐는가"만 봐서 둘의 상호작용까지는 못 봄.
- **원인**: `orderIndex`를 `COUNT(*)`(그 태스크의 현재 항목 수)로 부여했음 — A(0), B(1), C(2)를 추가한 뒤 A를 삭제하면 남은 건 B(1), C(2)뿐인데, 다음에 D를 추가하면 count가 다시 2가 되어 C와 orderIndex가 충돌. 목록 조회 쿼리에도 보조 정렬 키가 없어서 충돌 시 순서가 요청마다 달라질 수 있었음.
- **해결**: 항목 추가 시 `orderIndex`를 `COUNT(*)` 대신 `MAX(orderIndex)+1`로 계산하도록 변경(리포지토리에 `COALESCE(MAX(...), -1)` 쿼리 추가), 목록 조회 쿼리에 `id ASC`를 보조 정렬로 추가(활동 로그·댓글 리포지토리에 이미 있던 것과 같은 패턴). 추가→삭제→추가 시나리오로 충돌이 안 나는지 회귀 테스트 추가.
- **결과**: "새 값을 카운트 기반으로 부여하는 방식은 삭제가 섞이는 순간 깨진다"는, 자동 증가 ID를 안 쓰고 애플리케이션에서 순번을 관리할 때 반복되는 함정. `MAX+1`이나 DB `AUTO_INCREMENT`류를 우선 고려해야 한다는 걸 다시 확인.

## [2026-09-08] 댓글 `updatedAt` 마이그레이션이 기존 행을 잘못된 값으로 백필하던 문제

- **상황**: 댓글 수정/삭제 기능(2개 태스크) 완료 후 전체 최종 리뷰에서 발견. 이 프로젝트에서 처음으로 `ALTER TABLE`을 쓰는 마이그레이션(`V7`)이었음(그 전까지는 전부 `CREATE TABLE`).
- **원인**: `ALTER TABLE task_comment ADD COLUMN updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP;` — `DEFAULT CURRENT_TIMESTAMP`는 기존 행에 대한 `NOT NULL` 제약 위반은 막아주지만, 그 값 자체는 "마이그레이션이 실행된 시각"이 된다. 그런데 `updatedAt`을 만든 목적 자체가 "생성 시엔 `createdAt`과 같고, 수정하면 달라진다"는 규칙으로 프론트가 "(수정됨)" 배지를 띄우는 거였음 — 이 마이그레이션이 실제 데이터가 있는 DB에 적용되면, 기존 댓글이 전부 `updatedAt > createdAt`이 되어 하나도 안 고친 댓글까지 전부 "수정됨"으로 보이게 됨. 테스트는 항상 빈 DB에서 시작하는 Testcontainers를 쓰기 때문에 이 백필 문제를 애초에 감지할 수 없는 구조였음(197/197 통과했지만 이 버그를 못 잡음).
- **해결**: 마이그레이션에 `UPDATE task_comment SET updated_at = created_at;` 한 줄을 추가해서, 기존 행은 각자의 `created_at`으로 백필되도록 수정. (이 마이그레이션이 아직 어떤 실제 DB에도 적용된 적 없다는 걸 `flyway_schema_history` 조회로 먼저 확인한 뒤, 새 버전 파일을 만들지 않고 `V7` 자체를 직접 고쳤다.)
- **결과**: "테스트 DB가 항상 비어서 시작하면, 마이그레이션의 백필 로직 자체는 테스트로 검증이 안 된다"는 걸 남긴 사례 — 이런 종류의 버그는 리뷰(특히 "이 값이 프로덕션의 기존 데이터에 어떻게 적용될까"를 의식적으로 묻는 리뷰)로만 잡을 수 있다.

## [2026-09-11] `@TransactionalEventListener(AFTER_COMMIT)`에서 알림 저장이 조용히 씹히던 문제

- **상황**: 알림 기능(태스크 이벤트 4종 → 인앱 알림) 구현 중, 담당자 지정/댓글/체크리스트완료/마감일임박
  이벤트를 실제로 발행시켜서 리스너가 `Notification`을 만드는지 확인하는 통합 테스트를 처음 돌렸는데,
  5개 중 4개가 "알림이 하나도 안 생김"으로 실패했다. 리스너 코드 자체는 브리프 그대로였고 로직에 눈에 띄는
  버그도 없어 보였다.
- **원인**: `NotificationService.notify(...)`가 (다른 서비스 메서드들과 똑같이) 기본 `@Transactional`
  (`Propagation.REQUIRED`)이었는데, 이게 `@TransactionalEventListener(phase = AFTER_COMMIT)` 안에서
  호출되는 게 문제였다. Spring의 `AbstractPlatformTransactionManager.processCommit()`은 `AFTER_COMMIT`
  콜백(`triggerAfterCommit()`)을 실제 트랜잭션 리소스 정리(`cleanupAfterCompletion()`)보다 **먼저** 실행한다
  — 그래서 콜백이 도는 시점엔 "방금 커밋된, 곧 정리될" 트랜잭션 동기화가 아직 활성 상태로 보인다. `REQUIRED`는
  이걸 "이미 트랜잭션이 있네"로 착각하고 새 트랜잭션을 안 열고 거기 합류해버리는데, 그 죽어가는 트랜잭션은
  다시 커밋될 일이 없어서 쓰기 자체가 어디에도 반영 안 되고 조용히 사라진다(에러도 안 남, ID도 null로 남음).
- **해결**: `notify()`의 전파 속성을 `Propagation.REQUIRES_NEW`로 바꿔서, `AFTER_COMMIT` 콜백 안에서 호출돼도
  항상 진짜 새 트랜잭션을 열고 그 자리에서 커밋하게 했다. 이 변경이 또 다른 두 가지 문제를 연쇄로 드러냈다:
  1. 기존 `NotificationServiceTest`(Task 1)가 전부 깨짐 — 테스트가 `AbstractIntegrationTest`의 클래스 레벨
     트랜잭션 안에서 유저를 만드는데, 그건 실제로 커밋된 적이 없어서 `REQUIRES_NEW`가 여는 별개 커넥션에서는
     그 유저가 안 보임(`UserNotFoundException`). → 테스트 헬퍼(`newUser`)에서
     `TestTransaction.flagForCommit()/end()/start()`로 실제 커밋시키는 걸로 해결.
  2. 딱 하나의 테스트(`alreadyNotifiedTodayIsFalseThenTrueAfterFirstNotify`)만 추가로 깨짐 — 쓰기 **전에**
     한 번 읽고 쓰기 **후에** 또 읽는 패턴이었는데, MySQL 기본 `REPEATABLE_READ`가 트랜잭션의 첫 읽기 시점에
     읽기 스냅샷을 고정해버려서, 그 뒤에 `REQUIRES_NEW`로 커밋된 내용을 같은 트랜잭션의 두 번째 읽기가 못 봄.
     → 쓰기와 두 번째 읽기 사이에 같은 `TestTransaction` 갱신을 한 번 더 넣어서 스냅샷을 새로 잡게 해서 해결.
  최종 리뷰(가장 강력한 모델)에서 세 가지 진단을 전부 독립적으로 재현(격리된 복사본에서 각 수정을 하나씩
  되돌려보는 A/B 실험)해서 "테스트만 우연히 통과한 게 아님"까지 확인했다. 리뷰에서 추가로 지적된 것 —
  수신자별 `notify()` 호출에 예외 처리가 없어서 한 명이라도 실패하면(예: 탈퇴한 유저) 나머지 수신자도 못
  받고, 예외가 커밋 이후까지 새어나가 "성공적으로 처리된 요청"이 사용자한텐 500으로 보일 수 있었던 것 —
  도 `notifySafely()` try/catch 래퍼로 같이 고쳤다.
- **결과**: `@TransactionalEventListener(AFTER_COMMIT)` 안에서 쓰기를 하려면 `REQUIRES_NEW`가 사실상
  필수라는 걸 실측으로 확인한 사례. 동시에 "`REQUIRES_NEW`로 고치면 같은 트랜잭션 안에서 테스트하던
  기존 테스트들이 깨질 수 있다"는 부작용도 남겼다 — 프로덕션 코드의 트랜잭션 경계를 바꾸는 수정은 그
  코드를 호출하는 테스트의 트랜잭션 가정도 같이 깨질 수 있다는 걸 다시 확인.

## [2026-09-12] "방금 100% 완료됨"이 계획서에서 "지금 100%임"으로 바뀌어 중복 알림을 만들던 문제

- **상황**: 알림 기능 전체 브랜치(7개 태스크) 최종 리뷰(가장 강력한 모델)에서 발견. 개별 태스크 리뷰
  때는 안 걸렸다 — 태스크 5 리뷰가 요구한 테스트 2개(마지막 항목 완료 시 알림 발행 / 마지막 아닌 항목
  완료 시 미발행)가 둘 다 통과했고, 코드도 계획서 그대로였다.
- **원인**: 설계 문서(`docs/superpowers/specs/2026-09-11-task-notifications-design.md`)는 체크리스트 완료
  알림 트리거를 "그 태스크의 체크리스트 전부가 **이제** `is_done=true`인지 재계산해서 **방금 100%로
  넘어갔으면** 발행"이라고 적었다. 그런데 이 프로즈를 구현 계획서(`docs/superpowers/plans/2026-09-11-
  task-notifications.md`)의 실제 코드로 옮기는 과정에서 "방금 전환됐는가"라는 조건이 빠지고 "지금
  전부 완료 상태인가"만 남았다:
  ```java
  if (Boolean.TRUE.equals(isDone) && isAllDone(taskId)) {
      eventPublisher.publishEvent(new ChecklistCompletedEvent(taskId));
  }
  ```
  이 조건은 "방금 마지막 항목을 체크해서 100%가 됨"과 "이미 100%인 태스크의 항목을 다시 한번 true로
  체크(멱등적 PATCH, 재시도, 더블클릭 등)"를 구분하지 못한다. 둘 다 `isDone==true`이고 그 직후
  `isAllDone(taskId)`도 true라서, 후자에서도 알림이 또 나간다. 계획서가 요구한 테스트 2개는 둘 다
  "전환되는 순간"만 검증했지 "이미 완료된 걸 다시 체크"하는 경로는 아예 안 건드려서, 통과해도 이 버그를
  못 잡는 구조였다.
- **해결**: 항목을 수정하기 **전에** 그 항목이 이미 done 상태였는지 캡처해두고, 그 값이 false였을 때만
  이벤트를 발행하도록 조건을 추가:
  ```java
  TaskChecklistItem item = findItem(taskId, itemId);
  boolean wasAlreadyDone = item.isDone();
  ...
  if (Boolean.TRUE.equals(isDone) && !wasAlreadyDone && isAllDone(taskId)) {
      eventPublisher.publishEvent(new ChecklistCompletedEvent(taskId));
  }
  ```
  이미 완료된 항목을 다시 `true`로 PATCH해도 알림이 재발행되지 않는지 확인하는 회귀 테스트
  (`recheckingAlreadyDoneItemDoesNotNotifyAgain`)를 추가했다.
- **결과**: "스펙 프로즈의 시간적 뉘앙스(방금 vs 지금)가 코드로 옮겨지면서 조용히 사라질 수 있다"는 걸
  남긴 사례. 개별 태스크 리뷰가 요구한 테스트는 계획서 자체가 정해준 것이라, 계획서의 요구사항 자체가
  불완전하면 그 테스트도 똑같이 불완전해져서 못 잡는다 — 이런 종류의 버그는 "계획서가 스펙의 의도를
  정확히 담았는가"를 다시 묻는 전체 리뷰에서만 걸린다는 걸 보여준 케이스. 같은 최종 리뷰에서
  `@TransactionalEventListener(AFTER_COMMIT)` 예외 격리가 `notify()` 호출 하나만 감싸고 앞단(`getTask`
  등)은 안 감싸져 있던 것도 같이 발견돼 고쳤다 — 커밋 이후 예외가 새어나가 성공한 요청이 500으로 보이는
  문제를 막으려던 원래 의도(`docs/troubleshooting.md`의 2026-09-11 AFTER_COMMIT 항목)가 한 겹 얕게만
  적용돼 있었던 것.

## [2026-09-12] 웹소켓 구독 권한 체크가 화이트리스트가 아니라 블랙리스트였던 문제

- **상황**: 태스크 실시간 변경 브로드캐스트(STOMP) 기능의 서브프로젝트 1을 SDD로 구현했다. 태스크별
  태스크 1(연결 인증+구독 권한 체크 인터셉터), 태스크 2(이벤트 발행+브로드캐스터)는 각각 개별 리뷰를
  클린으로 통과했는데, 전체 브랜치 최종 리뷰(opus)에서 두 태스크의 "조합"에서만 드러나는 심각한 인가
  우회 구멍이 나왔다.
- **원인**: `TaskTopicChannelInterceptor.handleSubscribe`가 **화이트리스트가 아니라 블랙리스트**로
  짜여 있었다 — destination이 `/topic/tasks/{id}` 정규식과 **일치하지 않으면** 그냥 조용히 통과시키는
  구조(개발자가 "이상한 destination은 안전할 테니 굳이 막을 필요 없다"고 무의식적으로 가정한 것). 그런데
  Spring의 심플 인메모리 브로커는 구독 destination을 `AntPathMatcher`로 패턴 매칭한다 — 즉 클라이언트가
  `/topic/tasks/*`나 `/topic/**` 같은 **패턴 자체**를 구독 destination으로 보내면, 그건 정규식과
  "일치하지 않으니" 인터셉터를 그냥 통과했고, 브로커는 그 패턴에 매칭되는 모든 태스크의 브로드캐스트를
  실제로 배달했다. 결과: 워크스페이스 멤버십 체크가 있으나 마나 — 유효한 JWT만 있으면 아무 워크스페이스
  소속이 아니어도 시스템 전체 태스크의 변경 신호를 다 받을 수 있었다. 같은 최종 리뷰에서 STOMP `SEND`
  프레임을 인터셉터가 아예 검사하지 않는다는 것도 같이 나왔다 — `setApplicationDestinationPrefixes`가
  설정 안 돼 있어서 클라이언트의 SEND가 서버 핸들러를 거치지 않고 브로커로 직행, 인증된 사용자면 누구나
  임의의 태스크 토픽에 가짜 브로드캐스트를 주입할 수 있었다.
- **해결**: `handleSubscribe`를 화이트리스트(deny-by-default)로 뒤집었다 — destination이 정규식과
  **정확히 일치하지 않으면 예외를 던진다**(반대로 이전엔 일치하면만 체크, 아니면 통과). `preSend`에
  `StompCommand.SEND`를 무조건 거부하는 분기도 추가. 두 인터셉터 개별 태스크 리뷰는 각자 "이 프레임/
  destination이 올 때 뭘 체크하는가"만 봤을 뿐, "브로커가 실제로 무엇을 매칭 규칙으로 쓰는가", "이
  인터셉터가 처리 안 하는 프레임 종류는 뭐가 있고 그게 안전한가"라는, 두 컴포넌트 경계에 걸친 질문은
  아무도 안 물어봤다 — 그래서 두 개별 리뷰 모두 클린으로 통과했는데도 조합에서 크리티컬 구멍이 남아있던
  것. `TaskChangeBroadcaster`에도 알림 기능 때와 같은 이유로 try/catch를 추가(AFTER_COMMIT 리스너 예외가
  커밋 후 호출자에게 새어나가 성공한 요청을 500으로 만드는 문제, `docs/troubleshooting.md`의
  2026-09-11 항목과 동일 패턴).
- **결과**: "개별 태스크 리뷰가 다 통과해도 전체 브랜치 리뷰가 따로 필요한 이유"를 실측으로 보여준
  사례 — 화이트리스트/블랙리스트 뒤바뀜과 SEND 미검사 둘 다 각 컴포넌트만 보면 "그럴듯"했지만, 실제
  배포 인프라(Spring 심플 브로커의 패턴 매칭 동작)를 조합해봐야만 드러나는 문제였다. 인가 체크를 짤 때
  "이 조건에 해당하면 막는다"가 아니라 "이 조건에 해당하는 것만 허용하고 나머지는 다 막는다"로 항상
  기본값을 뒤집어 생각해야 한다는 교훈.

  통과했고, 실제 STOMP 클라이언트로 붙는 e2e 테스트까지 다 통과했는데, 전체 브랜치 최종 리뷰(opus)에서
  "같은 태스크를 두 명이 동시에 보면 어떻게 되는가"라는 이 기능의 핵심 시나리오 자체가 깨져 있다는 걸
  발견했다 — 정확히 서브프로젝트 1 때와 같은 패턴: 개별 태스크는 각자 다 맞는데, 조합에서만 드러나는
  문제.
- **원인**: 프레즌스 북키핑(로컬 `ConcurrentHashMap`과 Redis Hash 필드)을 **STOMP 세션ID나 구독ID
  하나만으로** 키를 잡았다. 그런데 STOMP 구독 ID는 클라이언트가 정하는 값이고 "한 연결 안에서만" 고유하면
  된다는 게 프로토콜 규칙이라, 실제 STOMP 클라이언트(Spring `DefaultStompSession`, stomp.js 등)는 거의
  항상 각 연결의 첫 구독을 `"0"`으로 매긴다. 그러니까 같은 태스크를 보는 두 사람이 각자 다른 연결로
  들어와도 둘 다 구독 ID `"0"`을 쓰는 게 일반적인 상황인데, 북키핑 맵이 이 값 하나로만 키가 잡혀 있으니
  **두 번째 사람이 구독하는 순간 첫 번째 사람의 북키핑 항목을 그냥 덮어썼다**. 더 나쁜 건, 이게 단순히
  "누구 목록에 누가 잘못 표시되는" 수준이 아니라 — 먼저 들어온 사람이 나중에 연결을 끊어도
  `handleDisconnect`가 세션ID로 필터링해서 그 항목을 찾으려 하는데, 이미 두 번째 사람의 항목으로
  덮어써진 뒤라 **아무 것도 찾지 못해서 정리(퇴장 브로드캐스트조차)가 아예 안 일어나고**, Redis에 영구
  유령 뷰어로 남는 문제였다. e2e 테스트가 이걸 못 잡은 이유: 기존 테스트는 항상 "마지막에 구독한 세션"을
  끊는 시나리오만 검증했는데, 마침 그 경우엔 자기 자신의 항목이 온전히 남아있어서 우연히 통과했다.
- **해결**: 로컬 맵과 Redis 필드 양쪽 다 `세션ID + "::" + 구독ID` 합성키로 바꿨다. 처음엔 "Redis 쪽만
  고치면 되지 않을까"(로컬 맵은 구독 ID만으로도 괜찮을 것 같다는 가설)로 접근했는데, 직접 되돌려서
  재현 테스트를 돌려보니 그 가설 자체가 틀렸다는 게 실측으로 확인됐다 — 로컬 맵이 세션 간에 덮어써지는
  게 먼저 일어나는 문제라, Redis 쪽만 고쳐도 여전히 안 고쳐짐. "먼저 구독한 세션이 연결을 끊으면 남은
  세션에게 자기 자신만 남은 목록이 브로드캐스트되는지" 검증하는 회귀 테스트를 새로 추가해서, 수정 전
  코드로는 실패하고 수정 후엔 통과하는 것까지 확인했다. 같은 라운드에서 발견된 부수 문제 2개도 같이
  고쳤다: (1) STOMP `id` 헤더가 프로토콜상 필수가 아니라서 없으면 Redis 쓰기 후 로컬 기록이 NPE로
  실패해 미아 항목이 남을 뻔한 것(null 가드 + 쓰기 순서 조정), (2) 프레즌스 Redis 키에 TTL이 없어서
  서버가 재시작되면 인메모리 세션 추적은 사라지는데 Redis 데이터만 영구히 남는 것(다른 Redis 사용처와
  동일하게 TTL 추가).
- **결과**: "개별 태스크 리뷰가 다 통과하고 e2e 테스트까지 있어도, 그 테스트가 우연히 통과하기 쉬운
  경로만 짚고 있으면 핵심 버그를 놓칠 수 있다"는 걸 다시 한번 보여준 사례(서브프로젝트 1의 화이트리스트/
  블랙리스트 사건과 같은 급의 교훈, 다른 형태로). 클라이언트가 자유롭게 정할 수 있는 식별자(이번 경우
  STOMP 구독 ID)를 "충분히 고유하겠지"라고 가정하고 그대로 저장소 키로 쓰면, 그 가정이 깨지는 순간
  (동시 접속) 조용히 데이터가 뒤섞인다는 게 핵심 교훈 — 서버 쪽에서 진짜로 고유성을 보장할 수 있는
  값(세션ID)과 조합해서 합성키로 만들어야 안전했다.

## [2026-09-13] "특정 구독 하나만 서버가 조용히 강제 해제" — 공개 API가 없어서 Spring 내부 동작을 소스로 직접 검증한 사례

- **상황**: 워크스페이스에서 추방된 멤버가 소켓 연결을 안 끊으면 보드 브로드캐스트(전체 태스크 데이터

  필요했다. Spring은 이런 용도의 공개 API를 제공하지 않는다 — 세션 전체를 끊는 방법(ERROR 프레임 전송 +
  `session.close()`, 이 프로젝트가 SUBSCRIBE 거부 시 이미 쓰고 있는 방식)은 있어도, "이 세션의 이 구독만"
  없애는 문서화된 방법은 없다.
- **조사**: Spring 메시징 소스(`spring-messaging`/`spring-websocket` 7.0.8, 로컬 Gradle 캐시의
  `-sources.jar`를 직접 풀어서 읽음)를 뒤져서 찾은 우회로: `SimpleBrokerMessageHandler.handleMessageInternal`은
  들어오는 메시지가 `SimpMessageType.UNSUBSCRIBE`면 `AbstractSubscriptionRegistry.unregisterSubscription(message)`를
  호출하는데, 이 메서드는 메시지 헤더에서 `sessionId`/`subscriptionId`만 읽어서 처리한다 — **메시지가
  진짜 클라이언트 STOMP 프레임에서 왔는지는 전혀 검사하지 않는다.** 즉 이 두 헤더만 채운 합성 메시지를
  `clientInboundChannel`에 직접 보내면 실제 UNSUBSCRIBE 프레임과 동일하게 처리된다.
- **검증**: 이 우회로가 실제로 "조용히, 안전하게" 동작하는지는 최종 리뷰(opus)에서 같은 소스를 다시 파고들어
  확인했다. 우연히 우리 쪽에 유리하게 떨어진 지점이 두 군데 있었다:
  1. 합성 메시지엔 `destination` 헤더가 없는데, `AbstractBrokerMessageHandler.checkDestinationPrefix`는
     destination이 `null`이면 곧바로 `true`(통과)를 반환한다 — 반대로 구현됐다면 이 메시지 자체가 브로커
     단계에서 조용히 무시됐을 것.
  2. 이 프로젝트의 `TaskTopicChannelInterceptor.preSend`는 `MessageHeaderAccessor.getAccessor(message,
     StompHeaderAccessor.class)`로 STOMP 프레임인지 확인하는데, 합성 메시지의 `SimpMessageHeaderAccessor`는
     `StompHeaderAccessor`의 인스턴스가 아니라서 `null`을 반환하고 인터셉터가 그냥 통과시킨다 — 반대로
     이 인터셉터가 좀 더 느슨하게 아무 메시지나 다 검사하도록 짜여 있었다면 이 우회로 자체가 막혔을 것.

  또한 `DefaultSimpUserRegistry`(`SimpUser.getSessions()`/`SimpSession.getSubscriptions()`)가 매번 새
  `HashSet`으로 복사해서 반환한다는 것도 소스로 확인해서, 순회 중 구독 해제를 호출해도
  `ConcurrentModificationException`이 안 난다는 걸 추측이 아니라 사실로 확정했다.
- **결과**: 리뷰에서 나온 추가 지적(구독 범위를 넘어서는 부작용이 없는지 테스트로 직접 증명 안 돼 있었음,
  세션 여러 개 중 하나 처리 실패 시 나머지를 포기하고 넘어감) 둘 다 반영. 교훈: "표준 API가 없어서 내부
  구현에 의존하는 우회로"를 쓸 때는, 그 우회로가 의도한 대로 동작하는 이유를 문서(레퍼런스/블로그)가
  아니라 **그 버전의 실제 소스로 직접 검증**해야 한다 — 이번 경우처럼 "이렇게 될 것 같다"가 맞았어도, 그게
  맞은 이유가 여러 세부 동작(널 체크 방향, 타입 체크 방식)이 우연히 유리하게 겹친 결과라면, 다음
  버전업이나 비슷한 패턴을 다른 곳에 재사용할 때 똑같이 안전하다는 보장이 없다.

## [2026-09-13] `@Modifying(clearAutomatically = true)`만 켜면 직전 `deleteByTaskId`들이 조용히 유실됨

- **상황**: 태스크 전용 파일 첨부 기능(`WorkspaceFile`에 nullable `task_id` 추가) 구현 중, "태스크
  삭제 시 첨부 파일은 지우지 말고 일반 파일함으로 되돌린다"는 요구사항을 처음엔 마이그레이션의
  `ON DELETE SET NULL`만으로 해결하려 했다. 그런데 테스트에서 태스크 삭제 직전에 그 파일을 이미
  로딩(`confirm()`)해둔 상태라 Hibernate가 `TransientPropertyValueException`을 던졌다 — DB 레벨
  캐스케이드는 ORM이 전혀 모르기 때문에, 같은 영속성 컨텍스트에 이미 로딩된 엔티티가 삭제될 대상을
  참조하고 있으면 플러시 시점에 일관성 체크가 걸린다.
- **1차 시도와 그 부작용**: `TaskService.delete()`에서 명시적으로
  `WorkspaceFileRepository.clearTaskId(taskId)`(벌크 `UPDATE ... SET task = null`)를 호출하도록
  고치면서 `@Modifying(clearAutomatically = true)`만 켰다. 개별 테스트(`WorkspaceFileServiceTest`)는
  통과했는데, `TaskServiceTest`를 같이 돌리자 기존에 잘 통과하던 `deletingTaskAlsoDeletesActivityLogs`,
  `deletingTaskWithAssigneeAndCommentDoesNotThrow`, `deletingTaskAlsoDeletesChecklistItems` 3개가
  갑자기 실패했다 — 태스크 삭제 후에도 댓글/체크리스트/활동로그가 그대로 남아있다는 assertion 실패.
- **원인**: `TaskService.delete()`는 내 새 코드보다 먼저 `taskAssigneeRepository.deleteByTaskId`,
  `taskCommentRepository.deleteByTaskId`, `taskActivityLogRepository.deleteByTaskId`,
  `taskChecklistItemRepository.deleteByTaskId`를 호출한다. 이 파생(derived) delete 메서드들은 즉시
  DB에 반영되는 게 아니라, Hibernate가 실제 DELETE문을 **플러시 시점까지 미룬 채 영속성 컨텍스트에만
  예약**해둔다. 그런데 `@Modifying`의 `clearAutomatically = true`는 쿼리 실행 "후" 컨텍스트를 비우기만
  할 뿐, "전"에 먼저 플러시하지는 않는다(`flushAutomatically`가 별도 옵션, 기본값 `false`). 그래서 내
  벌크 UPDATE가 실행된 뒤 `clear()`가 호출되는 순간, 아직 플러시 안 된 채 대기 중이던 앞의 4개
  `deleteByTaskId` 예약이 DB에 한 번도 반영되지 못하고 그대로 증발했다 — 태스크는 지워지는데 딸린
  하위 데이터는 조용히 살아남는 버그.
- **해결**: `@Modifying(flushAutomatically = true, clearAutomatically = true)`로 둘 다 켰다.
  `flushAutomatically`가 먼저 대기 중인 변경사항을 DB에 반영한 뒤에 내 벌크 UPDATE를 실행하고, 그 다음
  `clearAutomatically`가 컨텍스트를 비워서 이후 조회가 최신 상태(방금 null로 바뀐 `task_id`)를 보게
  한다.
- **결과**: `@Modifying` 벌크 쿼리를 기존 엔티티 기반 삭제/수정 로직과 같은 트랜잭션에 섞어 쓸 때는
  `clearAutomatically`만으로는 부족하고 `flushAutomatically`도 항상 같이 켜야 한다는 게 실측으로 확인된
  교훈 — 그렇지 않으면 "직전에 예약된 변경이 조용히 사라지는" 종류의 버그가 생기는데, 격리된 단위
  테스트만으로는 절대 못 잡고(그 테스트는 앞선 `deleteByTaskId` 호출 자체가 없으니까) 전체 스위트를
  같이 돌려야만 드러난다 — 이 세션에서 반복해서 나온 "개별 리뷰/테스트는 통과해도 조합에서 깨지는" 패턴의
  또 다른 사례.

## [2026-09-13] STOMP UNSUBSCRIBE 프레임엔 destination이 없어서, 계획서가 직접 지정한 코드가 애초에 동작 불가능했던 사례

- **상황**: CRDT 실시간 공동편집 서브프로젝트 8번 태스크 — "편집 토픽 구독을 해제하면 남은 버퍼를
  즉시 저장 시도한다"는 리스너를 구현하는 중. 계획서(plan)가 직접 지정한 코드는
  `SessionUnsubscribeEvent`에서 `StompHeaderAccessor.getDestination()`을 읽어 어느 토픽인지 판단하는
  방식이었다.
- **원인**: 이 계획서의 가정 자체가 틀렸다. 실제 STOMP UNSUBSCRIBE 프레임은 SUBSCRIBE 때 클라이언트가
  정한 `id` 헤더만 싣고 다니고, destination은 아예 안 실린다 — SUBSCRIBE는 "무엇을 구독할지" 알려줘야
  하니 destination이 필수지만, UNSUBSCRIBE는 "그 구독 id를 취소한다"는 뜻이라 destination을 다시 보낼
  이유가 없기 때문. Spring 7.0.8 소스(`DefaultStompSession.unsubscribe()`, `StompSubProtocolHandler`)로
  직접 확인 — 클라이언트도, 서버도 UNSUBSCRIBE 프레임에 destination을 채워 넣는 코드가 어디에도 없다.
  그래서 계획서가 지정한 `accessor.getDestination()`은 항상 `null`을 반환해, 이 리스너는 실제 클라이언트
  UNSUBSCRIBE에 대해 단 한 번도 발동하지 못하는 죽은 코드였다.
- **해결**: 이미 같은 패키지에 있던 `TaskPresenceEventListener`가 정확히 같은 문제를 먼저 풀어놓은
  상태였다 — SUBSCRIBE 시점에 `(sessionId, subscriptionId) → 정보`를 인메모리에 기록해뒀다가, 나중에
  UNSUBSCRIBE가 (destination 없이) sessionId+subscriptionId만 들고 오면 그걸로 아까 기록해둔 정보를
  찾아 쓰는 패턴. 이번 리스너도 그대로 재사용해서 SUBSCRIBE 때 taskId/field를 기록해두고
  UNSUBSCRIBE 때 꺼내 쓰도록 고쳤다.
- **결과**: 사람이 쓴 설계 문서·구현 계획이라도 프로토콜 세부사항(이번엔 "STOMP 프레임 종류별로 정확히
  어떤 헤더가 실리는가")을 잘못 가정하면 그대로 죽은 코드가 될 수 있다 — 특히 이번 경우처럼 컴파일도
  되고, 단위 테스트도 (destination을 수동으로 채운 합성 이벤트로 테스트했다면) 통과했을 만한 종류의
  버그라 실제 STOMP 클라이언트로 end-to-end 테스트를 돌려보지 않았다면 프로덕션에서야 발견됐을 것.
  이미 같은 코드베이스에 같은 문제를 풀어놓은 선례(`TaskPresenceEventListener`)가 있다면, 계획서의
  글자 그대로보다 그 선례의 패턴을 우선시하는 게 맞다는 것도 확인.

## [2026-09-13] `enableSimpleBroker("/topic")`에 `/queue`가 빠져서 `/user/queue/...` 구독·전송이 조용히 무시되던 문제

- **상황**: 같은 서브프로젝트에서 "늦게 참여하는 사람에게 미저장 버퍼를 그 사람에게만 재생해주는"
  기능을 붙이면서 `SimpMessagingTemplate.convertAndSendToUser(...)` + `/user/queue/...` 구독을 처음
  도입. 테스트가 재생 메시지를 못 받고 계속 타임아웃.
- **원인**: Spring은 `/user/queue/...` 구독을 받으면 `UserDestinationMessageHandler`가 내부적으로
  `/queue/...-user<세션ID>`라는 실제(physical) 목적지로 바꿔서 브로커에 등록한다. 그런데
  `WebSocketConfig`는 `registry.enableSimpleBroker("/topic")`만 해놨었다 — 브로커가 관리하는
  프리픽스에 `/queue`가 없으니, 이 변환된 목적지는 브로커 어디에도 등록되지 않고 조용히 무시된다.
  에러도, 로그도 없이 그냥 아무 일도 안 일어난다.
- **해결**: `registry.enableSimpleBroker("/topic", "/queue")`로 `/queue` 프리픽스를 추가.
- **결과**: `convertAndSendToUser`/`/user/**` 구독을 새로 도입할 때는 브로커의 관리 프리픽스 목록에
  실제로 변환되는 목적지(`/queue/...` 등)가 포함돼 있는지부터 확인해야 한다 — 이 설정 하나가
  빠지면 인가 로직이나 비즈니스 로직은 전부 맞아도 기능 자체가 조용히 동작하지 않는다.

## [2026-09-13] "메타 키가 먼저 만료될까봐" 걱정하며 추가한 TTL 갱신이, 오히려 무한 재시도 루프를 만든 사례

- **상황**: 최종 브랜치 리뷰에서 나온 여러 지적사항을 한 번에 고치는 수정 묶음(fix wave) 중 하나로,
  "혹시 폴링과 저장 요청 사이에 메타 키의 TTL이 먼저 만료되면 살아있는 버퍼의 메타데이터만 사라질 수
  있다"는 (검증 안 된) 우려로 `TaskEditBufferService.markRequested()`에 메타 키 TTL 갱신 한 줄을
  추가했다. 스코프 재리뷰(재검증 담당 서브에이전트)가 이 한 줄이 새로운 회귀를 만들었다고 잡아냈다.
- **원인**: 애초에 그 우려의 전제가 틀렸다 — `appendUpdate()`가 버퍼 키와 메타 키 둘 다 같은 순간에
  TTL을 건다(`redisTemplate.expire(bufferKey, ...)`, `redisTemplate.expire(metaKey, ...)`가 나란히
  호출됨). 그래서 메타 키만 따로 먼저 만료될 방법이 없는데도, 방어적으로 메타 키의 TTL만 갱신하는
  코드를 추가해버렸다. 그 결과 자동저장 폴러가 `retry-seconds`마다 `markRequested()`를 호출할
  때마다(아무도 응답 안 하는 상황이 오래가면) 메타 키의 TTL이 계속 연장돼 사실상 영구히 살아남게
  됐다 — 반면 버퍼 키(실제 타이핑 데이터가 든)는 원래 TTL(1시간)대로 만료된다. `metadata()`는
  메타 키만 보고 판단하므로 계속 "버퍼가 있다"고 착각해서 저장 요청을 영원히 재발송한다 — 정확히
  이번 수정 묶음이 없애려던 그 "재시도 폭주" 버그를, 다른 경로로 되살린 셈.
- **해결**: 추가했던 TTL 갱신 한 줄을 그대로 되돌렸다.
- **결과**: "혹시 몰라서" 추가하는 방어적 코드는 그 우려가 실제로 근거가 있는지 먼저 확인해야 한다 —
  이번엔 근거 확인 없이 "동일한 패턴을 다른 메서드에도 똑같이 적용"(`appendUpdate`가 TTL을 갱신하니
  `markRequested`도 갱신하자)한 게 문제였다. 두 메서드가 다루는 두 키(버퍼/메타)의 생명주기가 원래는
  묶여 있었는데, 한쪽만 독립적으로 연장하면서 그 결합이 깨진 것 — "같은 패턴처럼 보이는 코드"를
  복붙하기 전에 왜 원본 코드가 그렇게 돼 있는지부터 이해해야 한다는, 흔하지만 재확인된 교훈.

## [2026-09-23] CI에서만 가끔 실패하는 `TaskEditRelayControllerTest` — `Thread.sleep()` 고정 대기 시간 플레이키니스

- **상황**: `feature/notification-settings` PR(#17)의 CI가 "Run tests"에서 실패. 로컬(Windows)에서는
  516개 테스트 전부 통과했는데 GitHub Actions(Ubuntu 러너)에서만 1개 실패
  (`TaskEditRelayControllerTest.snapshotForDescriptionPersistsToTaskAndClearsBuffer`). 이 PR이 건드린
  파일(`notification` 패키지)과는 전혀 무관한 `realtime` 패키지 테스트라 처음엔 당황스러웠음.
- **원인**: 이 테스트는 실제 STOMP 세션으로 메시지를 보낸 뒤 `Thread.sleep(300)`/`Thread.sleep(500)`
  같은 고정 시간만큼 기다렸다가 비동기로 반영된 DB 상태를 assert하는 구조. 로컬 개발 머신보다 느리거나
  부하가 있는 CI 러너에서는 그 시간 안에 STOMP 메시지 처리 + DB 반영이 끝나지 않을 수 있어서 간헐적으로
  실패한다 — PR의 실제 코드 변경과는 무관한, 원래부터 있던 테스트의 타이밍 취약성.
- **해결**: 코드를 고치지 않고 CI job을 재실행(Re-run failed jobs)했더니 통과. 실제 회귀가 아니었음을
  확인.
- **결과**: CI가 실패했을 때 "내가 방금 건드린 파일과 실패한 테스트 파일이 같은 영역인가"부터 먼저
  확인할 것 — 완전히 무관한 패키지의, 고정 `Thread.sleep()`에 의존하는 실시간/비동기 테스트라면 먼저
  재실행부터 시도해볼 가치가 있다. 이런 테스트들은 근본적으로 견고하지 않으니, 반복적으로 이 파일에서
  플레이키니스가 발생하면 `Thread.sleep()`을 폴링/`Awaitility` 같은 조건 기반 대기로 바꾸는 리팩토링을
  고려할 것.
