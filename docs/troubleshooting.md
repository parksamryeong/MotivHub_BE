## [2026-08-30] 프론트엔드 토큰 저장 전략 결정

- **상황**: 프론트(MotivHub_FE)에서 로그인 플로우를 붙이면서, `/api/auth/exchange`·`/api/auth/refresh`로 받은 accessToken/refreshToken을 어디에 저장할지 결정해야 했다. 후보는 (1) 둘 다 localStorage (2) accessToken은 메모리, refreshToken은 localStorage (3) refreshToken을 httpOnly 쿠키로.
- **원인**: (문제 상황 아님 — 설계 결정)
- **해결**:
  - **최종 선택은 (2) accessToken 메모리 보관 + refreshToken localStorage.** XSS가 발생해도 메모리에 있는 accessToken은 새로고침 시 사라지므로 탈취 후 악용 가능한 시간 창이 짧아진다. 대신 앱 진입 시 refresh 1회로 accessToken을 재발급받는 구조가 필요하다.
  - **(3) httpOnly 쿠키 방식은 채택하지 않음.** 이유는 보안이 아니라 백엔드 제약: 현재 `SecurityConfig`의 CORS 설정이 `allowCredentials: false`(쿠키 미사용, 토큰을 body/헤더로만 주고받는 구조)라서, 쿠키 기반으로 가려면 백엔드의 CORS·쿠키 발급(SameSite/Secure 속성 포함) 로직을 같이 바꿔야 한다. 지금 범위에서는 프론트 단독 변경만으로 완결되는 (2)를 택했다.
- **결과**: (수치 변화 없음 — 설계 결정 기록)
  - 트레이드오프 요약: (1) 둘 다 localStorage는 구현이 가장 단순하지만 XSS 시 refreshToken까지 영구 탈취되는 위험이 가장 크다. (2)는 구현 복잡도가 조금 늘지만(메모리 상태 관리 + 앱 진입 시 silent refresh) XSS 노출 창을 줄인다. (3) httpOnly 쿠키가 이론적으로 가장 안전하지만 지금 아키텍처(백엔드가 토큰을 body로 응답, CORS `allowCredentials: false`)와 맞지 않아 채택하지 않았다 — 향후 진짜 프로덕션으로 갈 때 재검토 대상.

## [2026-09-01] 새로고침하면 로그인이 가끔 풀리는 문제

- **상황**: 멀티 디바이스 로그인 기능(기기별로 독립적인 세션 유지)을 검증하던 중, 기기A에서 로그아웃한 뒤 기기B를 새로고침했더니 기기B도 로그아웃되는 현상 발견. 처음엔 백엔드의 기기별 Redis 키 분리 로직이 잘못된 줄 알았음.
- **원인**: 백엔드가 아니라 프론트 문제였음. Redis에서 남은 세션의 refresh token을 직접 꺼내 `/api/auth/refresh`에 curl로 재생해봤더니 200이 정상적으로 돌아와서, 서버 로직은 이상이 없다는 걸 먼저 확인. 그 다음 프론트 코드를 비교해보니 `App.tsx`의 앱 부팅 `useEffect`에 React 18 StrictMode의 이중 실행 방지 가드가 없었음 — 같은 로직을 쓰는 `OAuthCallbackPage.tsx`에는 이미 `hasRun` ref 가드가 있었는데 부팅 로직에는 빠져있었음. StrictMode가 effect를 두 번 실행 → `/api/auth/refresh`가 거의 동시에 두 번 호출 → 첫 요청이 refresh token을 rotate하면 두 번째 요청은 이미 무효화된 토큰으로 401 → 그 401의 실패 처리가 방금 첫 요청이 저장한 정상 로그인 상태를 지워버림.
- **해결**: `App.tsx`의 부팅 effect에 `OAuthCallbackPage.tsx`와 동일한 `hasRun` ref 가드를 추가해서 중복 실행 방지.
- **결과**: 새로고침 시 세션이 안정적으로 유지됨. 이 과정에서 "증상은 프론트에서 보이지만 원인은 프론트/백엔드 중 어느 쪽인지" 구분하는 방법(서버가 들고 있는 실제 데이터를 직접 조회 + 같은 요청을 수동으로 재생해서 서버 로직만 따로 검증)을 정리하게 됨 — 이후에도 비슷한 종류의 버그를 볼 때 재사용 가능한 접근.

## [2026-09-02] 초대 무효화 API의 권한 우회 취약점

- **상황**: 워크스페이스 초대(링크/이메일) 기능 코드 리뷰 중 `WorkspaceInviteService.revokeInvite(ownerUserId, workspaceId, inviteId)`를 점검하다가 발견.
- **원인**: 이 메서드는 호출자가 `workspaceId`의 OWNER인지는 확인했지만, 정작 지우려는 `inviteId`가 그 `workspaceId` 소속인지는 검증하지 않았음. 즉 아무 워크스페이스나 하나라도 OWNER인 사용자면, 다른 워크스페이스의 초대 ID를 추측/열거해서 무효화시킬 수 있는 구조(IDOR 유형).
- **해결**: 초대 조회에 `.filter(i -> i.getWorkspace().getId().equals(workspaceId))`를 추가해서 워크스페이스 불일치 시 "존재하지 않는 초대"와 같은 예외로 처리 — 다른 워크스페이스에 그 초대가 실재하는지 여부를 호출자에게 노출하지 않도록 함. 교차 워크스페이스 시나리오를 재현하는 회귀 테스트도 추가.
- **결과**: 리뷰 단계에서 배포 전에 잡힘. "권한 검사(OWNER 확인)"와 "리소스 소유 관계 검사(그 리소스가 그 상위 리소스 소속인지)"는 별개로 챙겨야 한다는 걸 코드에 남겨둔 사례.

## [2026-09-02] 목록 조회 API의 N+1 쿼리 개선

- **상황**: 워크스페이스 목록(`listMine`)과 태스크 목록(`listByWorkspace`) 조회 API 리뷰에서 각각 N+1 쿼리 패턴이 지적됨.
- **원인**: `@ManyToOne(fetch = LAZY)` 연관관계를 `stream().map(...)` 안에서 항목별로 개별 접근 — 목록 항목 수만큼 추가 쿼리가 발생하는 구조였음(멤버 목록에서 각 멤버의 워크스페이스, 태스크 목록에서 각 태스크의 담당자).
- **해결**: `listMine`은 리포지토리 쿼리를 `JOIN FETCH`로 변경해서 한 번에 가져오도록, `listByWorkspace`는 담당자를 `findByTaskIdIn(...)`으로 배치 조회한 뒤 메모리에서 태스크별로 그룹핑하는 방식으로 변경.
- **결과**: 항목 N개 기준 쿼리 수가 N+1에서 1~2회로 감소. 지금 규모(개인/소규모 팀 프로젝트)에서는 체감 차이가 크진 않지만, 코드 리뷰에서 이런 패턴을 습관적으로 잡아내는 연습이 됨.

## [2026-09-06] Swagger/OpenAPI가 모든 프로필에서 인증 없이 공개되어 있던 문제

- **상황**: 워크스페이스/태스크 보완 작업(이름 수정 API, 초대 목록 조회 API, 응답 닉네임 embed) 완료 후 전체 브랜치 diff에 대한 최종 리뷰를 돌리던 중 발견. 이번 작업 범위는 아니었지만(springdoc-openapi Swagger 문서 추가는 그 이전 커밋에서 이미 들어간 상태) 리뷰 중 "이상한 게 있으면 알려달라"는 취지로 넓게 훑다가 걸림.
- **원인**: `SecurityConfig`의 `PUBLIC_ENDPOINTS`에 `/v3/api-docs/**`, `/swagger-ui/**`, `/swagger-ui.html`이 프로필 구분 없이 `permitAll`로 등록되어 있었고, springdoc 자체를 끄거나 프로필별로 조건화할 방법이 어디에도 없었음. 즉 실제 배포 환경에 그대로 올라가면 인증 없이 전체 API 명세(모든 엔드포인트, 모든 DTO 필드 구조)가 누구에게나 노출되는 구조. `application.yaml`에 이미 actuator에 대해서는 "로컬 전용, 실배포시 네트워크 격리/인증 반드시 추가"라는 주석이 있었는데, Swagger는 그런 주석이나 대비책 없이 추가된 것으로 보임.
- **해결**: `application.yaml`에 `springdoc.api-docs.enabled`/`springdoc.swagger-ui.enabled`를 `${SWAGGER_ENABLED:false}`로 설정해서 기본값을 "꺼짐"으로 바꿈(secure-by-default) — 환경변수 하나로 로컬에서만 켤 수 있게 함. springdoc 자체가 꺼지면 해당 엔드포인트가 아예 등록되지 않아 `SecurityConfig`의 `permitAll` 여부와 무관하게 404가 남. 다만 이렇게 하면 테스트 프로필에서 Swagger 접근 가능을 검증하던 기존 `SecurityConfigTest`(`apiDocsAreAccessibleWithoutAuth`, `swaggerUiIsAccessibleWithoutAuth`)가 깨지므로, `application-test.yaml`에 같은 프로퍼티를 `true`로 덮어써서 테스트 환경에서는 그대로 열려있도록 함.
- **결과**: 배포 시 별도 설정 없이도 API 명세가 비공개로 시작하는 구조가 됨. 기존 테스트는 프로필 오버라이드로 그대로 통과. "새 기능 추가할 때 편의성 있는 문서화 도구(Swagger 등)를 붙이면서 보안 기본값을 놓치기 쉽다"는 걸 다시 확인한 사례 — actuator 때는 이미 주석으로 남겨뒀던 걸 Swagger 때는 놓쳤음.

## [2026-09-07] 활동 로그 컬럼 폭이 감사 대상 컬럼보다 좁아서 태스크 수정이 통째로 롤백되던 문제

- **상황**: 활동 로그 + 체크리스트 8개 태스크 SDD 작업 완료 후 전체 브랜치 최종 리뷰(가장 강력한 모델로 별도 실행)에서 발견. 태스크별 스코프 리뷰에서는 각 diff가 다 정상으로 보였는데, 전체를 한 번에 보는 단계에서만 드러난 케이스.
- **원인**: `TaskActivityLog.oldValue`/`newValue`는 `VARCHAR(500)`인데, 이 값에 그대로 들어가는 `Task.description`은 `VARCHAR(2000)`(최대 2000자 허용)였음. 500자 넘는 설명으로 `PATCH /api/tasks/{id}`를 호출하면 활동 로그 INSERT가 컬럼 폭을 넘겨서 MySQL strict mode에서 `DataIntegrityViolationException` 발생 → `@Transactional` 메서드 전체가 롤백 → 사용자 입장에선 정상적인 요청인데 500 에러와 함께 수정 내용이 통째로 날아감. Task 1(활동 로그 인프라)과 태스크 상세 정보(description 2000자 허용)는 서로 다른 태스크에서 각각 정상으로 구현됐지만, 둘의 "폭" 제약이 서로 안 맞는다는 건 두 diff를 동시에 안 보면 안 보이는 문제였음.
- **해결**: `TaskActivityLogService.record(...)`에서 `field`/`oldValue`/`newValue`를 각 컬럼 폭(30/500/500)으로 저장 전에 truncate하도록 방어 로직 추가 — 어떤 호출부가 와도 컬럼을 못 넘기게 원천 차단. 600자 설명으로 수정해도 예외 없이 성공하고 로그의 `newValue`가 정확히 500자로 잘리는지 회귀 테스트 추가.
- **결과**: "감사/로그용 스냅샷 컬럼의 폭은 그게 감사하는 원본 컬럼의 폭과 반드시 맞춰서 확인해야 한다"는 걸 남긴 사례. 태스크 단위 리뷰는 "이 diff가 스펙대로 됐는가"만 보고, 전체 리뷰가 "여러 태스크가 합쳐지면 뭐가 깨지는가"를 본다는 두 리뷰의 역할 차이를 실제로 보여준 케이스이기도 함.

## [2026-09-07] 체크리스트 orderIndex가 삭제 후 재사용되면서 정렬이 충돌하던 문제

- **상황**: 같은 최종 리뷰에서 함께 발견. 체크리스트 항목 추가(Task 5)와 삭제(Task 6)가 서로 다른 태스크에서 구현됐는데, 각 태스크의 스코프 리뷰는 "이 태스크가 요구사항대로 됐는가"만 봐서 둘의 상호작용까지는 못 봄.
- **원인**: `orderIndex`를 `COUNT(*)`(그 태스크의 현재 항목 수)로 부여했음 — A(0), B(1), C(2)를 추가한 뒤 A를 삭제하면 남은 건 B(1), C(2)뿐인데, 다음에 D를 추가하면 count가 다시 2가 되어 C와 orderIndex가 충돌. 목록 조회 쿼리에도 보조 정렬 키가 없어서 충돌 시 순서가 요청마다 달라질 수 있었음.
- **해결**: 항목 추가 시 `orderIndex`를 `COUNT(*)` 대신 `MAX(orderIndex)+1`로 계산하도록 변경(리포지토리에 `COALESCE(MAX(...), -1)` 쿼리 추가), 목록 조회 쿼리에 `id ASC`를 보조 정렬로 추가(활동 로그·댓글 리포지토리에 이미 있던 것과 같은 패턴). 추가→삭제→추가 시나리오로 충돌이 안 나는지 회귀 테스트 추가.
- **결과**: "새 값을 카운트 기반으로 부여하는 방식은 삭제가 섞이는 순간 깨진다"는, 자동 증가 ID를 안 쓰고 애플리케이션에서 순번을 관리할 때 반복되는 함정. `MAX+1`이나 DB `AUTO_INCREMENT`류를 우선 고려해야 한다는 걸 다시 확인.

## [2026-09-11] 부하테스트 확장 — 읽기 위주 신규 기능 API

## [2026-09-08] 댓글 `updatedAt` 마이그레이션이 기존 행을 잘못된 값으로 백필하던 문제

- **상황**: 댓글 수정/삭제 기능(2개 태스크) 완료 후 전체 최종 리뷰에서 발견. 이 프로젝트에서 처음으로 `ALTER TABLE`을 쓰는 마이그레이션(`V7`)이었음(그 전까지는 전부 `CREATE TABLE`).
- **원인**: `ALTER TABLE task_comment ADD COLUMN updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP;` — `DEFAULT CURRENT_TIMESTAMP`는 기존 행에 대한 `NOT NULL` 제약 위반은 막아주지만, 그 값 자체는 "마이그레이션이 실행된 시각"이 된다. 그런데 `updatedAt`을 만든 목적 자체가 "생성 시엔 `createdAt`과 같고, 수정하면 달라진다"는 규칙으로 프론트가 "(수정됨)" 배지를 띄우는 거였음 — 이 마이그레이션이 실제 데이터가 있는 DB에 적용되면, 기존 댓글이 전부 `updatedAt > createdAt`이 되어 하나도 안 고친 댓글까지 전부 "수정됨"으로 보이게 됨. 테스트는 항상 빈 DB에서 시작하는 Testcontainers를 쓰기 때문에 이 백필 문제를 애초에 감지할 수 없는 구조였음(197/197 통과했지만 이 버그를 못 잡음).
- **해결**: 마이그레이션에 `UPDATE task_comment SET updated_at = created_at;` 한 줄을 추가해서, 기존 행은 각자의 `created_at`으로 백필되도록 수정. (이 마이그레이션이 아직 어떤 실제 DB에도 적용된 적 없다는 걸 `flyway_schema_history` 조회로 먼저 확인한 뒤, 새 버전 파일을 만들지 않고 `V7` 자체를 직접 고쳤다.)
- **결과**: "테스트 DB가 항상 비어서 시작하면, 마이그레이션의 백필 로직 자체는 테스트로 검증이 안 된다"는 걸 남긴 사례 — 이런 종류의 버그는 리뷰(특히 "이 값이 프로덕션의 기존 데이터에 어떻게 적용될까"를 의식적으로 묻는 리뷰)로만 잡을 수 있다.
