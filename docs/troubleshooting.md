## [2026-08-27] 첫 부하테스트 — 보호 API 기준선 확보

- **상황**: Docker Compose + Prometheus + Grafana로 관측 인프라를 구축한 뒤, k6로 `GET /api/users/me`, `GET /api/users/me/mypage`에 ramping 부하(0→50명→0, 3분)를 줘서 실제로 지표가 움직이는지, 그리고 지금 시점 성능이 어느 정도인지 확인했다.
- **원인**: (문제 상황 아님 — 최초 기준선 측정)
- **해결**: (해당 없음)
- **결과**:
  - 총 11,864 요청, 실패 0건 (성공률 100%)
  - 처리량 약 65.6 req/s (VU 50명 유지 구간)
  - 응답시간: 평균 10ms, p95 13.83ms, 최대 217.43ms
  - Grafana 대시보드에서 TPS/JVM 힙 패널이 부하 구간과 정확히 같은 모양(상승→유지→하강)으로 실시간 반영되는 것 확인
  - 현재 규모(조회 API 2개, 50 VU)에서는 병목이 전혀 보이지 않음 — 이후 기능이 늘어나거나 VU를 더 올렸을 때 이 수치와 비교해 성능 저하 여부를 판단할 기준선으로 사용

## [2026-08-30] 프론트엔드 토큰 저장 전략 결정

- **상황**: 프론트(MotivHub_FE)에서 로그인 플로우를 붙이면서, `/api/auth/exchange`·`/api/auth/refresh`로 받은 accessToken/refreshToken을 어디에 저장할지 결정해야 했다. 후보는 (1) 둘 다 localStorage (2) accessToken은 메모리, refreshToken은 localStorage (3) refreshToken을 httpOnly 쿠키로.
- **원인**: (문제 상황 아님 — 설계 결정)
- **해결**:
  - **최종 선택은 (2) accessToken 메모리 보관 + refreshToken localStorage.** XSS가 발생해도 메모리에 있는 accessToken은 새로고침 시 사라지므로 탈취 후 악용 가능한 시간 창이 짧아진다. 대신 앱 진입 시 refresh 1회로 accessToken을 재발급받는 구조가 필요하다.
  - **(3) httpOnly 쿠키 방식은 채택하지 않음.** 이유는 보안이 아니라 백엔드 제약: 현재 `SecurityConfig`의 CORS 설정이 `allowCredentials: false`(쿠키 미사용, 토큰을 body/헤더로만 주고받는 구조)라서, 쿠키 기반으로 가려면 백엔드의 CORS·쿠키 발급(SameSite/Secure 속성 포함) 로직을 같이 바꿔야 한다. 지금 범위에서는 프론트 단독 변경만으로 완결되는 (2)를 택했다.
- **결과**: (수치 변화 없음 — 설계 결정 기록)
  - 트레이드오프 요약: (1) 둘 다 localStorage는 구현이 가장 단순하지만 XSS 시 refreshToken까지 영구 탈취되는 위험이 가장 크다. (2)는 구현 복잡도가 조금 늘지만(메모리 상태 관리 + 앱 진입 시 silent refresh) XSS 노출 창을 줄인다. (3) httpOnly 쿠키가 이론적으로 가장 안전하지만 지금 아키텍처(백엔드가 토큰을 body로 응답, CORS `allowCredentials: false`)와 맞지 않아 채택하지 않았다 — 향후 진짜 프로덕션으로 갈 때 재검토 대상.

## [2026-09-01] 새로고침하면 로그인이 가끔 풀리는 문제

- **상황**: 멀티 디바이스 로그인 기능(기기별로 독립적인 세션 유지)을 검증하던 중, 기기A에서 로그아웃한 뒤 기기B를 새로고침했더니 기기B도 로그아웃되는 현상 발견. 처음엔 백엔드의 기기별 Redis 키 분리 로직이 잘못된 줄 알았음.
- **원인**: 백엔드가 아니라 프론트 문제였음. Redis에서 남은 세션의 refresh token을 직접 꺼내 `/api/auth/refresh`에 curl로 재생해봤더니 200이 정상적으로 돌아와서, 서버 로직은 이상이 없다는 걸 먼저 확인. 그 다음 프론트 코드를 비교해보니 `App.tsx`의 앱 부팅 `useEffect`에 React 18 StrictMode의 이중 실행 방지 가드가 없었음 — 같은 로직을 쓰는 `OAuthCallbackPage.tsx`에는 이미 `hasRun` ref 가드가 있었는데 부팅 로직에는 빠져있었음. StrictMode가 effect를 두 번 실행 → `/api/auth/refresh`가 거의 동시에 두 번 호출 → 첫 요청이 refresh token을 rotate하면 두 번째 요청은 이미 무효화된 토큰으로 401 → 그 401의 실패 처리가 방금 첫 요청이 저장한 정상 로그인 상태를 지워버림.
- **해결**: `App.tsx`의 부팅 effect에 `OAuthCallbackPage.tsx`와 동일한 `hasRun` ref 가드를 추가해서 중복 실행 방지.
- **결과**: 새로고침 시 세션이 안정적으로 유지됨. 이 과정에서 "증상은 프론트에서 보이지만 원인은 프론트/백엔드 중 어느 쪽인지" 구분하는 방법(서버가 들고 있는 실제 데이터를 직접 조회 + 같은 요청을 수동으로 재생해서 서버 로직만 따로 검증)을 정리하게 됨 — 이후에도 비슷한 종류의 버그를 볼 때 재사용 가능한 접근.

## [2026-09-02] 초대 무효화 API의 권한 우회 취약점

- **상황**: 워크스페이스 초대(링크/이메일) 기능 코드 리뷰 중 `WorkspaceInviteService.revokeInvite(ownerUserId, workspaceId, inviteId)`를 점검하다가 발견.
- **원인**: 이 메서드는 호출자가 `workspaceId`의 OWNER인지는 확인했지만, 정작 지우려는 `inviteId`가 그 `workspaceId` 소속인지는 검증하지 않았음. 즉 아무 워크스페이스나 하나라도 OWNER인 사용자면, 다른 워크스페이스의 초대 ID를 추측/열거해서 무효화시킬 수 있는 구조(IDOR 유형).
- **해결**: 초대 조회에 `.filter(i -> i.getWorkspace().getId().equals(workspaceId))`를 추가해서 워크스페이스 불일치 시 "존재하지 않는 초대"와 같은 예외로 처리 — 다른 워크스페이스에 그 초대가 실재하는지 여부를 호출자에게 노출하지 않도록 함. 교차 워크스페이스 시나리오를 재현하는 회귀 테스트도 추가.
- **결과**: 리뷰 단계에서 배포 전에 잡힘. "권한 검사(OWNER 확인)"와 "리소스 소유 관계 검사(그 리소스가 그 상위 리소스 소속인지)"는 별개로 챙겨야 한다는 걸 코드에 남겨둔 사례.

## [2026-09-02] 목록 조회 API의 N+1 쿼리 개선

- **상황**: 워크스페이스 목록(`listMine`)과 태스크 목록(`listByWorkspace`) 조회 API 리뷰에서 각각 N+1 쿼리 패턴이 지적됨.
- **원인**: `@ManyToOne(fetch = LAZY)` 연관관계를 `stream().map(...)` 안에서 항목별로 개별 접근 — 목록 항목 수만큼 추가 쿼리가 발생하는 구조였음(멤버 목록에서 각 멤버의 워크스페이스, 태스크 목록에서 각 태스크의 담당자).
- **해결**: `listMine`은 리포지토리 쿼리를 `JOIN FETCH`로 변경해서 한 번에 가져오도록, `listByWorkspace`는 담당자를 `findByTaskIdIn(...)`으로 배치 조회한 뒤 메모리에서 태스크별로 그룹핑하는 방식으로 변경.
- **결과**: 항목 N개 기준 쿼리 수가 N+1에서 1~2회로 감소. 지금 규모(개인/소규모 팀 프로젝트)에서는 체감 차이가 크진 않지만, 코드 리뷰에서 이런 패턴을 습관적으로 잡아내는 연습이 됨.
